# Smart Nature Wind v0203 웹 화면 재설계 (제품 구매자 관점)

## 1. 진단 — 왜 어수선한가

현재 UI는 개발자/파워유저를 기준으로 설계되었고, 구매자는 이 제품을 "선풍기"로 샀다는 사실이 설계 전제에서 빠져 있습니다.

### 1.1 정량적 복잡도 측정

| 항목 | 현재 수치 | 문제점 |
| :--- | :--- | :--- |
| **최상위 페이지** | 14개 | 네비게이션만으로 피로도 가중 |
| **대시보드 카드** | 6개 (mode/state/power/sensor/preset/slider) | 첫 화면이 설정판처럼 복잡함 |
| **대시보드 버튼/토글** | 30개 이상 | 시선 분산 및 조작 혼선 |
| **프리셋 × 스타일 조합** | 10 × 5 = 50가지 | 선택 조합 간 관계 불명확 |
| **FSM 상태 노출** | 7개 상태 + reason 12개 | 사용자 관심사 아님 (개발자 관점) |
| **물리 파라미터 노출** | intensity/variability/gust 3종 상시 | 초보자에게 조작 공포감 유발 |
| **AI 기능** | L4 잠금 (숨김) | 일반 구매자도 활용하고 싶음 |
| **개발자용 화면** | 로그/진단/WS설정/NVS 메인 네비 포함 | 양산 제품에는 노출 불필요 |

### 1.2 사용자 관점 시나리오 실패 지점

```
[구매자 최초 사용]
박스 개봉 → WiFi 연결 → 브라우저 접속 → 대시보드
                                                 ↓
                              🚨 첫 화면에 "프로필 모드/스케줄 모드" 
                                 스위치가 있음 → 이게 뭐지?
                              🚨 프리셋 8개 + 스타일 5개 + 슬라이더 3개
                                 = 어디부터 눌러야?
                              🚨 "AutoOff", "PIR", "runSource", "FSM"
                                 같은 개발자 용어 노출
```

핵심 모순: CT10_Ctl_0203.h의 FSM은 7-state(OVERIDE/PROFILE_RUN/SCHEDULE_RUN/MOTION_BLOCKED/AUTOOFF_STOPPED/TIME_INVALID)이지만, 구매자에게 필요한 상태는 3개: 켜짐/꺼짐/자동꺼짐.

## 2. 재설계 철학 (50년차 원칙)

### 원칙 A: "선풍기 하나로 30초 안에 시원함"

- 구매 결정 요인은 사용 첫 30초의 감동. 스펙이 아님.
- 대시보드는 "전원 ON + 프리셋 선택" 두 동작만 노출.

### 원칙 B: 점진적 공개 (Progressive Disclosure) 3단

| 계층 | 대상 | 노출 기능 |
| :--- | :--- | :--- |
| **L1 필수 (90%)** | 모든 구매자 | 전원, 프리셋, 수면모드, 타이머 |
| **L2 개인화 (9%)** | 애호가 | 스케줄, 스타일, 자동화 |
| **L3 전문가 (1%)** | 매니아 | 로그, 진단, 펌웨어, 커스텀 프리셋 |

현재는 모든 계층이 L3를 봐야 함. 재설계는 L1을 기본값으로.

### 원칙 C: "자동화"는 별도 세계

- 스케줄/프로필/모드전환 = 한 화면(자동화) 으로 통합
- 대시보드에 "스케줄 모드 / 프로필 모드" 스위치 금지

### 원칙 D: 기술 용어 → 감성 용어

| 현재 (기술 용어) | 재설계 (감성/사용자 용어) |
| :--- | :--- |
| `AUTOOFF_STOPPED` | 🌙 취침 종료 |
| `MOTION_BLOCKED` | 👋 자리 비움 감지 |
| `OVERRIDE` | ✋ 수동 조절 중 |
| `TIME_INVALID` | 🕐 시간 미동기 |
| `runSource=2` | *(사용자 화면 숨김)* |
| `PWM 55%` | 🌊 잔잔한 바람 |

### 원칙 E: "설정"과 "조작"의 분리

- 조작 = 홈 (1개)
- 탐색 = 바람 (1개)
- 자동화 = 자동화 (1개)
- 관측 = 모니터 (1개)
- 시스템 = 설정 (1개)
- AI = 모든 화면 우하단 FAB (floating action button)

## 3. 새로운 정보구조 (IA)

14 페이지 → 5 페이지 (64% 축소)

```
[메인 네비 - 하단 탭 바]
┌──────────────────────────────────────────┐
│   🏠      🌬️      ⏰      📊      ⚙️    │
│  홈      바람    자동화   모니터   설정  │
└──────────────────────────────────────────┘

[플로팅]
                              ┌────────────┐
                              │  🤖 AI     │  ← 우하단 상시
                              └────────────┘
```

| 새 페이지 | 통합된 기존 페이지 | 역할 |
| :--- | :--- | :--- |
| **🏠 홈** | `dashboard` (축소) | 전원 + 즐겨찾기 + 타이머 |
| **🌬️ 바람** | `dashboard(preset)` + `windprofile` + `simulation` | 프리셋 선택 + 미세조정 |
| **⏰ 자동화** | `schedule` + `profiles` + `(timer 승격)` | 반복 실행 계획 |
| **📊 모니터** | `chart` + `sensors` + `monitor(숨김)` | 관측 + 이력 |
| **⚙️ 설정** | `settings` + `network` + `logs` + `diagnostics` + `firmware` + `info` | 시스템 관리 |

삭제/이동 매트릭스

| 기존 페이지 | 재설계 처리 방안 |
| :--- | :--- |
| `Dashboard` | ➔ **홈** (축소) + **바람** (이동) |
| `Chart` | ➔ **모니터** 통합 |
| `Schedule` | ➔ **자동화** 탭 1 |
| `Profiles` | ➔ **자동화** 탭 2 |
| `Sensors` | ➔ **모니터** (통합) |
| `Simulation` | 페이지 단독 삭제 (➔ **바람** 화면 내 프리뷰로 흡수) |
| `WindProfile` | ➔ **설정 > 고급** |
| `Settings` | ➔ **설정** (탭 재편) |
| `Network` | ➔ **설정 > 네트워크** |
| `Logs` | ➔ **설정 > 고급** |
| `Diagnostics` | ➔ **설정 > 고급** |
| `Firmware` | ➔ **설정 > 고급** |
| `AI` | ➔ **FAB 승격** (페이지 삭제, 모든 화면 접근) |
| `Info` | ➔ **설정 > 일반** |

삭제되는 개념

- ❌ 모드 스위치 (Schedule / Profile) — "자동 실행"이면 스케줄 on, 아니면 off로 충분
- ❌ L1~L4 레벨 시스템 — 모든 기능 접근 가능, L3 기능은 접힌 아코디언으로
- ❌ A/B 비교, Tasting tour — 개발자용
- ❌ WS 채널 설정, NVS 스펙 — 개발자용, 고급 안에만
- ❌ AUTOOFF ACK 모달 — 상단 배너 + 원터치 재개
- ❌ 스타일 상시 노출 — 프리셋 선택 후에만 스타일 노출

홈 화면 핵심 설계 결정

결정 근거
전원 버튼이 화면 40% 선풍기의 본질은 "켜고 끄기". 터치 미스 방지
즐겨찾기 4개만 노출 10개 전부 노출 → 결정 마비. 4개면 충분
고급 설정 접힘 90% 사용자는 열지 않음
센서는 요약만 상세는 모니터
타이머 = 원터치 가장 자주 쓰는 자동화 기능이라 홈에 승격
상태 문구 = 감성 "OVERIDE" 대신 "수동 조절 중"

상태 표현 매핑 (FSM 7 → 4)

CT10 FSM 홈 표시
IDLE ⏻ "꺼짐"
OVERRIDE / PROFILE_RUN / SCHEDULE_RUN 🍃 "자연풍 가동 중"
MOTION_BLOCKED 👋 "자리 비움 - 자동 정지" (배너)
AUTOOFF_STOPPED 🌙 "취침 종료 - [다시 켜기]" (배너)
TIME_INVALID 🕐 "시간 미동기" (경고 아이콘만)

AUTOOFF ACK 모달 → 상단 배너로 교체:


## 6. 기능 재설계 상세 (선풍기 관점)

### 6.1 전원 제어 (핵심)

| 현재 상태/방식 | 재설계 개선안 |
| :--- | :--- |
| 작은 토글 + ACK 모달 | 화면 40% 차지하는 직관적인 큰 원형 버튼 |
| AutoOff 시 차단 모달 노출 | 상단 인라인 배너 + `[다시 켜기]` 원터치 |
| MOTION_BLOCKED 시 별도 팝업 | 안내 배너 + `[강제 켜기]` 버튼 |
| 3단계 함정 진단 (모션/오토오프/타임) | 시스템 자동 처리 + 1탭 즉시 재개 |

### 6.2 속도 조절 = 프리셋 + 스타일

| 계층 | 표현 | 사용자 인지 |
| :--- | :--- | :--- |
| **프리셋 (10)** | 🌊 바다 / 🌲 숲속 / 🏔️ 산 등 | 감성적 자연풍 선택 |
| **스타일 (5)** | ⚖ 균형 / ⚡ 활동 / 🎯 집중 / 🍃 휴식 / 🌙 수면 | 바람 세기 및 뉘앙스 조정 |
| **물리 파라미터 (3)** | 강도 / 변동성 / 돌풍 | 전문가 전용 (고급 아코디언) |

"1-2-3단"이 사라짐 — 이 제품의 USP(자연풍)를 UI로 정당화.

### 6.3 자동 종료 (AutoOff)

| 현재 방식 | 재설계 개선안 |
| :--- | :--- |
| 스케줄 편집 내 "스마트 안전 종료" 아코디언 | 자동화 > 타이머 (홈 화면 원터치 승격) |
| offTime / offTemp 세부 옵션 노출 | 프로필 편집 내부로 격리 (파워유저용) |
| AutoOff 래치 시 모달 ACK 필수 | 상단 배너 안내 + 원터치 재개 |

### 6.4 PIR (인체 감지)

| 현재 방식 | 재설계 개선안 |
| :--- | :--- |
| 센서 페이지에 상세 설정 상시 노출 | 모니터 화면에서 상태 확인 위주로 간소화 |
| "PIR 강제 감지 테스트" 버튼 상시 노출 | **설정 > 고급** 메뉴로 이동 (설치/디버깅 전용) |
| PIR holdSec 상시 조정 | **자동화 > 프로필 편집** 내부 옵션으로 배치 |

### 6.5 센서 표시

| 현재 방식 | 재설계 개선안 |
| :--- | :--- |
| 별도 Sensors 페이지 (3카드 분리) | 홈 하단 미니 요약 + 모니터 상세 화면 통합 |
| 매초 지속 갱신 (네트워크 낭비) | 탭 진입 시 및 필요 시에만 지능적 갱신 |
| 숫자 중심 표기 (24.5°C) | 직관적 감성 의미 부여 ("쾌적", "건조" 라벨) |

### 6.6 수면 모드 (강조)

현재: 5 스타일 중 하나로 숨김
재설계: 홈 화면 원터치 버튼

```
[🔊 미리듣기]      [🌙 수면 모드]      [⏱️ 1시간 후 종료]
```

탭 시 자동으로:

- 프리셋: FOREST_CANOPY
- 스타일: SLEEP
- 강도: 25% (물리 하한)
- 타이머: 8시간 (조정 가능)
- LED: 끔

# Profile - Schedule - Step 재설계 + Simulation·Chart 부활

## Part 1. Step 개념 도입 — Profile/Schedule 관계 명확화

### 1.1 현재 구조의 문제 (코드 진단)

현재 코드에서 Schedule과 Profile은 병렬 구조이며 중복입니다:

```cpp
// C10_Config_Sch_0203.h
ST_A20_ScheduleItem_t {          ST_A20_UserProfileItem_t {
    schId/schNo                      profileId/profileNo
    period (요일+시간)      ←차이→    (없음)
    segments[]             ←동일→    segments[]
    repeatSegments         ←동일→    repeatSegments
    repeatCount            ←동일→    repeatCount
    autoOff                ←동일→    autoOff
    motion                 ←동일→    motion
}                                }
```

결과:

- CT10::tickSchedule() → schedule.segments[] 사용
- CT10::tickUserProfile() → profile.segments[] 사용
- 같은 로직이 두 벌로 존재 (tickSegmentSequence() 오버로드 2개)

사용자 인지 실패:

"스케줄"과 "프로필"이 무슨 차이인지 모르겠다
→ 실제 차이는 "시간 트리거가 있냐 없냐" 뿐

### 1.2 재설계 — 3계층 모델 (Step → Profile → Schedule)

```
┌─────────────────────────────────────────────────────┐
│  STEP (원자 단위)                                   │
│  "이 순간 어떤 바람을 얼마나"                        │
│  ─────────────────────────────────────────────      │
│  - 대상: 🌊 바다 / 🌲 숲속 / ⚙️ 고정풍속            │
│  - 세기: 잔잔 / 보통 / 강함                          │
│  - 지속: 20분                                        │
│  - 감성: "잔잔한 바다 20분"                          │
└─────────────────────────────────────────────────────┘
                        ↓ 여러 개 묶음
┌─────────────────────────────────────────────────────┐
│  PROFILE (바람 시나리오)                            │
│  "이런 흐름으로 바람이 이어졌으면 좋겠다"             │
│  ─────────────────────────────────────────────      │
│  - Step 1: 🌊 바다 - 20분                           │
│  - Step 2: ⏸ 휴지 - 5분                            │
│  - Step 3: 🌲 숲속 - 30분                           │
│  - 반복: 2회                                        │
│  - 감성: "바다 → 숲속 리듬 시나리오"                 │
└─────────────────────────────────────────────────────┘
                        ↓ 시간 트리거 참조
┌─────────────────────────────────────────────────────┐
│  SCHEDULE (자동 실행 계획)                          │
│  "언제 이 시나리오를 자동 실행할까"                   │
│  ─────────────────────────────────────────────      │
│  - 요일: 월~금                                      │
│  - 시간: 08:00 ~ 12:00                              │
│  - 실행: 📋 프로필 "아침 시원함" 참조                │
│  - 감성: "평일 아침마다 자동 실행"                   │
└─────────────────────────────────────────────────────┘
```

핵심 규칙:

| 계층 | SSOT 모델 | 역할 | 재사용성 |
| :--- | :--- | :--- | :--- |
| **Step** | 개념 모델 (구현: `ST_A20_ScheduleSegment_t` 재사용) | 원자 단위 바람 블록 ("무엇을 얼마나") | 단독 실행 불가 |
| **Profile** | `ST_A20_UserProfileItem_t` (단일화) | Step 시퀀스 (재생 가능한 플레이리스트) | **N개 Schedule이 공유 참조** |
| **Schedule** | `ST_A20_ScheduleItem_t` (재설계) | 시간 트리거 + profileId 외래키 참조 | 반복 스케줄러 |

변경점:

- ❌ Schedule이 segments[]를 직접 보유하던 구조 폐기
- ✅ Schedule은 profileId 하나만 참조 (외래키)
- ✅ Profile이 유일한 Step 시퀀스 소유자

### 1.3 코드 재설계 (핵심 스니펫)

```cpp
// [신규] Step = 기존 Segment 명칭 변경 (구조 유지, 의미 명확화)
typedef struct {
    uint8_t  stepNo;                    // 순서
    uint16_t durationMin;               // 지속 시간 (on+off 통합)
    
    // 바람 종류
    EN_A20_step_type_t type;            // PRESET | FIXED | REST(휴지)
    char     presetCode[24];            // type=PRESET일 때
    char     styleCode[24];             // type=PRESET일 때
    float    fixedSpeed;                // type=FIXED일 때
    ST_A20_SegmentOverride_t override;  // 선택적 물리 오버라이드
} ST_A20_Step_t;

// [재설계] Profile = Step 시퀀스 (유일한 소유자)
typedef struct {
    uint8_t  profileId;
    uint16_t profileNo;
    char     name[32];
    bool     enabled;
    
    uint8_t  stepCount;
    ST_A20_Step_t steps[MAX_STEPS];     // ← 유일한 Step 배열
    bool     repeat;                    // 시퀀스 반복
    uint8_t  repeatCount;
    
    ST_A20_AutoOff_t autoOff;           // 시퀀스 전체에 대한 안전 종료
    ST_A20_Motion_t  motion;            // PIR 재실 조건
} ST_A20_Profile_t;

// [재설계] Schedule = 트리거만 (segments 필드 완전 삭제!)
typedef struct {
    uint8_t  schId;
    uint16_t schNo;
    char     name[32];
    bool     enabled;
    
    ST_A20_SchedulePeriod_t period;     // 요일 + 시간 윈도우
    uint8_t  profileId;                 // ★ 참조 (외래키)
    
    // ▼ 선택적 오버라이드 (특수 케이스만)
    bool     overrideProfile;           // 이 스케줄에서만 프로필 대체
    ST_A20_AutoOff_t autoOffDelta;      // 프로필 autoOff에 가산
} ST_A20_Schedule_t;
```

tickSchedule() 리팩터:

```cpp
bool CL_CT10_ControlManager::tickSchedule() {
    // 1) Schedule → Profile 해석 (1단계)
    const auto& sch = schedules[schIdx];
    const auto& prof = findProfileById(sch.profileId);
    if (!prof.enabled) return false;
    
    // 2) Profile의 Step 시퀀스 실행 (기존 로직 재사용)
    return tickStepSequence(prof.steps, prof.stepCount, 
                            prof.repeat, prof.repeatCount,
                            scheduleStepRt);  // ← 단일 오버로드
}
```

## Part 6. 결론 — 왜 이 재설계가 구매자에게 이득인가

| 사용자 시나리오 | Before (0203 레거시) | After (재설계 모델) |
| :--- | :--- | :--- |
| **"매일 아침 같은 바람을 원해"** | 스케줄마다 세그먼트를 매번 재입력 | 프로필 1개 생성 후 복수 스케줄에서 외래키 참조 |
| **"바람이 실제로 어떤 느낌인지 모르겠어"** | 텍스트 프리셋 이름만 보고 맹목적 선택 | Simulation(바람 스튜디오) 모달에서 3초 체감 후 확정 |
| **"지난밤 수면 모드가 잘 작동했나?"** | ❌ 확인 불가 | 회고 탭에서 의도 vs 실제 오버레이 및 편차 리포트 확인 |
| **"이 설정 그대로 잘 돌아가고 있나?"** | ❌ 확인 불가 | 실시간 탭에서 현재 실행 컨텍스트 및 단계 직관적 표기 |
| **"어제랑 오늘 바람이 뭐가 달랐지?"** | ❌ 비교 불가 | 세션 요약 카드로 일자별 풍속 통계 즉각 비교 |

핵심 원칙 재확인:

- Step = "무엇을"의 최소 단위
- Profile = "어떤 순서로"의 시나리오 → 재사용 가능
- Schedule = "언제"의 트리거 → 프로필 참조만
- Simulation = "실행 전 상상" (개념적 손익분기점)
- Chart = "실행 후 회고" (사용자 신뢰 구축)

이 5가지가 유기적으로 연결되면, 사용자는 "감으로 쓰는 선풍기"에서 "의도대로 제어되는 자연풍 기기" 로 인식이 바뀝니다. 이게 이 제품의 진짜 USP입니다.

# Profile의 이중 실행 모델 — 수동 재생 + 스케줄 자동

좋은 지적입니다. Profile은 "재생 가능한 바람 플레이리스트" 로 정의하면, 이것이 수동 재생되든 스케줄로 재생되든 근본적으로 같은 것이어야 합니다. 현재 코드의 가장 큰 설계 결함은 이 둘을 완전히 다른 실행 경로(tickSchedule vs tickUserProfile)로 나눈 것입니다.

## 1. 핵심 개념 확정 — "재생 가능한 플레이리스트"

```
┌─────────────────────────────────────────────────┐
│  Profile = 바람 플레이리스트                     │
│  (Spotify 플레이리스트와 동일한 사고)            │
│                                                 │
│  - Step 1: 🌊 바다 - 20분                       │
│  - Step 2: ⏸ 휴지 - 5분                        │
│  - Step 3: 🌲 숲속 - 30분                       │
└─────────────────────────────────────────────────┘
              ↓              ↓
       [▶ 지금 재생]     [⏰ 스케줄 등록]
        (수동 트리거)     (자동 트리거)
              ↓              ↓
     ══════════════════════════════
       동일한 실행 엔진 (CT10)
       동일한 Step 시퀀스 재생 로직
     ══════════════════════════════
              ↓
       🌀 같은 바람이 나온다
```

원칙: 트리거 방식은 다르되, 실행 결과는 100% 동일해야 한다.

## 2. 두 트리거 방식 — 명확한 구분

| 실행 트리거 | 정의 | 지속 방식 | 종료 조건 |
| :--- | :--- | :--- | :--- |
| **수동 재생 (`MANUAL`)** | 사용자가 "▶ 지금 실행" 직접 탭 | **Sticky** (완료까지 유지) | ① 플레이리스트 완료<br>② 사용자 수동 정지<br>③ AutoOff 타이머 만료<br>④ 다른 프로필 전환 |
| **스케줄 재생 (`SCHEDULE`)** | 설정된 스케줄 시간 윈도우 진입 | **시간 종속** (윈도우 종료 시) | ① 플레이리스트 완료<br>② 시간 윈도우 이탈<br>③ 수동 개입 (Manual 전환)<br>④ AutoOff 만료 |

차이의 본질은 "누가 언제 시작/종료를 결정하나" 이지, "무엇을 재생하나"가 아니다.

## 5. 실행 엔진 — decideRunSource() 단순화

### 5.1 재설계 후 우선순위

```
[1] overrideState.active
    → OVERRIDE (수동 강제, 스케줄/프로필 무시)

[2] _autoOffLatched
    → AUTOOFF_STOPPED (재개 전까지 차단)

[3] N10.manualProfileNo > 0  (수동 재생 중)
    ├─ 프로필 있음 → PROFILE_RUN (trigger=MANUAL)
    └─ 프로필 없음 → 수동 해제, [4]로

[4] 스케줄 시간 윈도우 진입
    ├─ 매칭 스케줄 있음 → 프로필 참조 → PROFILE_RUN (trigger=SCHEDULE)
    └─ 없음 → [5]

[5] IDLE
```

핵심: 수동이 항상 스케줄보다 우선 (사용자의 명시적 개입 > 자동화).

### 5.2 코드 (의사)

```cpp
ST_CT10_Decision_t CL_CT10_ControlManager::decideRunSource() {
    // 1) Override
    if (overrideState.active) 
        return { .state = OVERRIDE, .trigger = NONE };
    
    // 2) AutoOff 래치
    if (_autoOffLatched) 
        return { .state = AUTOOFF_STOPPED };
    
    // 3) 수동 재생 (최우선)
    int16_t manNo = CL_N10_NvsManager::getManualProfileNo();
    if (manNo > 0) {
        int idx = findProfileByNo(manNo);
        if (idx >= 0 && profiles[idx].enabled) {
            if (isMotionBlocked(profiles[idx].motion))
                return { .state = MOTION_BLOCKED, .trigger = MANUAL, ... };
            return { .state = PROFILE_RUN, .trigger = MANUAL, .profileIdx = idx };
        }
        // 프로필 삭제됨 → 자동 해제
        CL_N10_NvsManager::setManualProfileNo(0);
    }
    
    // 4) 스케줄
    if (!timeValid) return { .state = TIME_INVALID };
    
    int schIdx = findActiveScheduleIndex(*schedules, true);
    if (schIdx >= 0) {
        uint8_t pid = schedules->items[schIdx].profileId;
        int profIdx = findProfileById(pid);
        if (profIdx < 0) {
            // 프로필 삭제됨 → 스케줄 무효화 (경고 로그)
            return { .state = IDLE, .reason = PROFILE_MISSING };
        }
        if (isMotionBlocked(profiles[profIdx].motion))
            return { .state = MOTION_BLOCKED, .trigger = SCHEDULE, ... };
        return { .state = PROFILE_RUN, .trigger = SCHEDULE, 
                 .profileIdx = profIdx, .schIdx = schIdx };
    }
    
    // 5) Idle
    return { .state = IDLE };
}
```

## 6. 수동 재생 라이프사이클

### 6.1 시작 (▶ 지금 실행 탭)

```
UI 탭
  ↓
CT10::startProfileManual(profileNo)
  ↓
N10::setManualProfileNo(profileNo)   ← 영속화
  ↓
markDirty("state") → 다음 tick에서 실행
```

### 6.2 종료 조건 (4가지)

| 종료 조건 | 시스템 처리 로직 |
| :--- | :--- |
| **플레이리스트 완료** | `repeatCount` 소진 또는 Step 시퀀스 종료 ➔ `N10::setManualProfileNo(0)` 클리어 |
| **사용자 수동 정지** | 홈 화면의 `[⏹ 정지]` 탭 ➔ `N10::setManualProfileNo(0)` 즉시 클리어 |
| **AutoOff 발동** | `_autoOffLatched = true` 발동 ➔ 수동 재생 및 팬 구동 완전 정지 |
| **다른 프로필 전환** | `startProfileManual(다른No)` 호출 ➔ 이전 세션 종료 후 신규 프로필 교체 |

### 6.3 스케줄 재생과의 상호작용

| 경합 상황 | 시스템 우선순위 동작 |
| :--- | :--- |
| **수동 재생 중, 스케줄 시간 진입** | **수동 유지** (사용자 직접 조작 우선, 스케줄은 대기) |
| **수동 재생 종료, 스케줄 시간 유효** | **스케줄 자동 재개** (다음 제어 주기 `tick`에서 자동 복귀) |
| **스케줄 재생 중, 수동 재생 시작** | **수동으로 즉시 전환** (진행 중인 스케줄 즉시 중단) |
| **스케줄 재생 중, 시간 윈도우 이탈** | **`IDLE` 자동 복귀** (스케줄 정상 종료) |

핵심 원칙: 수동은 "재생 가능한 플레이리스트의 즉시 실행"이고, 스케줄은 "시간이 되면 자동 실행". 사용자의 명시적 개입(수동)이 항상 우선.

## 10. 마이그레이션 (기존 사용자 데이터 보호)

0203 → 0203 버전업 시 JSON 변환:

```javascript
// pio_gzip_0203.py의 마이그레이션 스텝
function migrate_0203_to_0203(json) {
  // 1) 기존 userProfiles → profiles (그대로, segments→steps 명칭만)
  json.userProfiles.profiles.forEach(p => {
    p.steps = p.segments; delete p.segments;
    p.steps.forEach(s => {
      s.type = s.mode === 'FIXED' ? 'FIXED' : 'PRESET';
      s.durationMin = s.onMinutes + s.offMinutes;  // 통합
    });
  });
  
  // 2) 기존 schedules → 익명 프로필 자동 생성 + 참조
  json.schedules.schedules.forEach(sch => {
    if (sch.segments && sch.segments.length > 0) {
      const anonProfileId = nextProfileId++;
      json.userProfiles.profiles.push({
        profileId: anonProfileId,
        profileNo: nextProfileNo++,
        name: `[자동 변환] ${sch.name}`,
        steps: sch.segments,  // 복사
        repeat: sch.repeatSegments,
        repeatCount: sch.repeatCount,
        autoOff: sch.autoOff,
        motion: sch.motion
      });
      sch.profileId = anonProfileId;
      delete sch.segments;
      delete sch.repeatSegments;
      delete sch.repeatCount;
      delete sch.autoOff;
      delete sch.motion;
    }
  });
  
  return json;
}
```

사용자는 아무것도 안 해도 됨 — 자동으로 새 구조로 변환, 기존 스케줄 그대로 작동. "익명 프로필"이 프로필 탭에 나타나 사용자가 리네임/편집 가능.

11. 결론 — 이중 트리거 모델의 가치

| 사용자 상황 | Before (0203 레거시) | After (재설계 모델) |
| :--- | :--- | :--- |
| **스케줄 없이 프로필 재생** | ❌ 개념 자체 없음 | ✅ **[▶ 재생] 원터치 즉시 실행** |
| **동일 바람을 2개 이상 스케줄에 사용** | 세그먼트 중복 입력 강제 | ✅ **프로필 1개 참조** |
| **프로필 수정 시 파급 효과** | 스케줄에 반영되지 않음 | ✅ **모든 참조 스케줄에 자동 반영** |
| **트리거 확인** | `runSource` 숫자만 노출 | ✅ **"✋ 수동" / "⏰ 스케줄" 직관적 뱃지** |
| **수동 개입 후 자동 복귀** | 모드 스위치 수동 조작 필요 | ✅ **자동 복귀 (수동 종료 시)** |
| **재부팅 후 상태 복원** | 스케줄만 복원 | ✅ **수동 선택도 NVS 복원** |

핵심: Profile = 재생 가능한 리소스, Schedule = 시간 트리거, Manual = 즉시 트리거. 이 세 개념을 분리하면:

- 90% 사용자 (스케줄만): 기존과 동일
- 9% 사용자 (수동만): 새 기능 (스케줄 학습 불필요)
- 1% 사용자 (혼합): 우선순위 명확

코드는 줄고(-40% 로직), UX는 명확해지고, 재사용성은 폭발합니다.

## Part 1. 기능 관점 (Functional Requirements)

### F1. 데이터 모델 — 3계층 재설계

#### F1.1 핵심 개념

| 계층 | 정의 | 재사용성 | 사용자 관점 인지 |
| :--- | :--- | :--- | :--- |
| **Step** | 원자적 바람 블록 ("무엇을 얼마나") | ❌ 단독 재사용 불가 | *"잔잔한 바다 20분"* |
| **Profile** | Step 시퀀스 = 재생 가능한 플레이리스트 | ✅ **N개 Schedule이 참조** | *"아침 시나리오"* |
| **Schedule** | 시간 트리거 (요일 + 시간 윈도우) | - | *"평일 08:00 자동 실행"* |

#### F1.2 Step 정의

```
Step = {
  stepNo       : 순서 (1..N)
  durationMin  : 지속 시간 (분)
  type         : PRESET | FIXED | REST
  presetCode   : type=PRESET일 때 (예: OCEAN)
  styleCode    : type=PRESET일 때 (예: BALANCE)
  fixedSpeed   : type=FIXED일 때 (%)
  override     : 선택적 물리 오버라이드 (강도/변동성/돌풍)
}
```

규칙:

- Step은 Profile 내부에서만 존재 (독립 리소스 아님)
- Step 편집/삭제는 Profile 편집 시에만 가능
- Step 개수: 1~8개 (MAX_SEGMENTS_PER_PROFILE 유지)

#### F1.3 Profile 정의 (재생 가능한 플레이리스트)

```
Profile = {
  profileId    : uint8 (자동 발급)
  profileNo    : uint16 (사용자 지정)
  name         : "아침 시원함"
  enabled      : bool
  
  stepCount    : 1~8
  steps[]      : Step 배열
  repeat       : bool (시퀀스 반복 여부)
  repeatCount  : 0=무한, N=반복 횟수
  
  autoOff      : 자동 종료 조건 (타이머/시각/온도)
  motion       : PIR 재실 조건
}
```

규칙:

- Profile은 Step 시퀀스의 유일한 소유자
- Profile 삭제 시 참조하는 Schedule 자동 무효화
- repeatCount=0 = 무한 재생 (수동 재생 시 유용)

#### F1.4 Schedule 정의 (트리거 참조)

```
Schedule = {
  schId        : uint8
  schNo        : uint16
  name         : "평일 아침"
  enabled      : bool
  
  period       : { days[7], startTime, endTime }
  profileId    : uint8 (외래키, Profile 참조)
}
```

변경 원칙:

- ❌ segments[] 필드 완전 삭제 (기존 중복 구조 폐기)
- ❌ repeatSegments, repeatCount, autoOff, motion 삭제 (Profile이 소유)
- ✅ profileId 참조만 유지

#### F1.5 참조 무결성

상황 처리
Profile 삭제 시 참조 Schedule 존재 삭제 확인 모달 + Schedule enabled=false 자동 전환
Schedule 실행 시 Profile 미존재 IDLE + 경고 로그 (PROFILE_MISSING)
Profile 비활성화 참조 Schedule은 유효하지만 실행 안 됨

---

### F2. 이중 트리거 실행 모델 ★핵심

#### F2.1 트리거 종류

| 실행 트리거 | 정의 | 지속 방식 | 우선순위 |
| :--- | :--- | :--- | :--- |
| **`OVERRIDE`** | 수동 강제 제어 (슬라이더 조작) | 명시 종료까지 | **최우선** |
| **`MANUAL`** | 사용자 "▶ 지금 실행" 탭 | 완료까지 Sticky 유지 | **1순위** |
| **`SCHEDULE`** | 시간 윈도우 진입 | 시간 윈도우 종속 | **2순위** |

#### F2.2 우선순위 규칙

```
[1] OVERRIDE (수동 강제) — 모든 자동 무시
     ↓ 없으면
[2] AUTOOFF_STOPPED (래치) — 재개 전 차단
     ↓ 없으면
[3] MANUAL (수동 재생) — 스케줄보다 우선
     ↓ 없으면
[4] SCHEDULE (시간 트리거)
     ↓ 없으면
[5] IDLE
```

원칙: 사용자의 명시적 개입(수동) > 자동화(스케줄)

#### F2.3 실행 결과 동일성 ★

- 동일 Profile이 MANUAL이든 SCHEDULE이든 동일한 Step 시퀀스 재생
- 실행 엔진 통합: tickProfile() 단일 함수
- 구분은 runCtx.trigger 필드로만 표시

#### F2.4 Manual 생명주기

시작 경로:

- 홈의 즐겨찾기 프로필 탭
- 자동화 > 프로필 탭의 [▶ 재생] 버튼
- (선택) AI 명령

종료 조건 (4가지):

| 종료 및 전환 조건 | 시스템 처리 로직 |
| :--- | :--- |
| **Step 시퀀스 완료 (`repeatCount` 소진)** | Manual 자동 해제 |
| **사용자 `[⏹ 정지]` 탭** | Manual 자동 해제 |
| **AutoOff 발동 (`_autoOffLatched=true`)** | Manual 정지 |
| **다른 프로필 Manual 재생** | 이전 Manual 자동 해제 후 교체 |

#### F2.5 재부팅 영속화

- NVS 키 man_prof (int16) 추가
- 부팅 시 복원:
  - >0 → 해당 Profile Manual 재생 재개
  - 0 → 스케줄 대기 모드
- 이유: 사용자가 명시 선택한 프로필이 재부팅 시 스케줄로 바뀌면 UX 파괴

#### F2.6 상호작용 시나리오 (검증 완료)

| 사용자 상호작용 시나리오 | 동작 및 실행 결과 |
| :--- | :--- |
| **스케줄 재생 중 ➔ 수동 재생 시작** | **`Manual`로 즉시 전환** (스케줄 중단) |
| **수동 재생 중 ➔ 스케줄 시간 진입** | **`Manual` 유지** (스케줄 대기) |
| **수동 재생 종료 ➔ 스케줄 시간 유효** | **스케줄 자동 재개** |
| **수동 재생 중 ➔ 스케줄 시간 이탈** | **영향 없음** (`Manual` 유지) |

## Part 5. 핵심 원칙 재확인

기능 관점

1. Profile = 재생 가능한 플레이리스트 (재사용 가능)
2. Schedule = 시간 트리거 + Profile 참조만 (Step 소유 안 함)
3. Manual > Schedule (사용자 개입 우선)
4. 트리거 방식 달라도 실행 결과 동일 (엔진 통합)
5. 재부팅 시 Manual 영속 (사용자 선택 보호)

UI 관점
