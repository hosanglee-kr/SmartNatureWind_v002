[C-1] while(!Serial) 무한 루프 — 스탠드얼론 배포 시 기기 먹통

위치: main.cpp setup()

```cpp
Serial.begin(115200);
delay(1500);
while (!Serial) {                    // ← USB 호스트 없으면 무한 대기
    delay(A20_Const::G_A00_USB_CDC_POLL_MS);
}
```

· ESP32-S3 Native USB CDC 모드(ARDUINO_USB_CDC_ON_BOOT=1)에서 USB 호스트 미연결 시 !Serial이 영원히 true
· PC 없이 전원만 인가하면 setup()에서 영구 정지 → Wi-Fi/제어/웹 모두 시작 안 됨
· 개발 환경에서만 테스트했다면 절대 드러나지 않는 버그

수정안:

```cpp
uint32_t t0 = millis();
while (!Serial && (millis() - t0 < 3000)) {   // 3초 타임아웃
    delay(A20_Const::G_A00_USB_CDC_POLL_MS);
}
```

[C-2] 대시보드 프리셋 그리드가 영원히 비어있음

위치: 200.page.dashboard.js mount()

```javascript
async mount() {
    this.el.innerHTML = ''; this.el.appendChild(SNW.Tpl.dashboard());
    try {
        const [stateData, profileData] = await Promise.all([...]);
        if (!this._active) return;
        this._applyInitialState(stateData);
        if (profileData) this._applyPresetList(profileData);   // ① components.presets 없음(no-op)
    } catch (e) { ... }
```

수정안: _mountComponents() 이후로 재배치하고 필요 시 데이터 재조회

```javascript
this._mountComponents();
this._bindStore();
if (profileData) this._applyPresetList(profileData);   // 컴포넌트 장착 후
```

[C-3] M10 isActive() — holdSec가 2배로 늘어남

위치: M10_MotionLogic_0202.h isActive()

```cpp
if (_state.pirActive) return true;
if (v_hold > 0 && (v_now - _state.lastChange_ms) < (v_hold * 1000UL))
    return true;   // ← 문제
```

_state.lastChange_ms는 상태가 바뀔 때마다(감지→활성, 활성→만료) 갱신됨:

· t=0: PIR 감지 → _state.pirActive=true, lastChange=0
· t=holdSec*1000: 만료 → _state.pirActive=false, lastChange=holdSec*1000
· t=holdSec*1000+1: 첫 조건 false, 두 번째 조건 (t - lastChange) < holdSec*1000 → true 반환

결과적으로 만료 후 다시 holdSec 동안 "활성" 상태 유지 → 실효 hold = 2×holdSec. holdSec=120초면 실제 240초간 fan 가동.

수정안: 두 번째 조건 삭제 (또는 lastChange_ms를 "감지 시점"만 기록)

```cpp
return _state.pirActive;   // 첫 조건만
```

_state.pirActive가 이미 hold 로직을 포함하므로 중복.

[A-1] WebSocket 브로드캐스트 스레드 안전성

CT10_WS_tick() (T-loop) → broadcastState() → AsyncWebSocketClient::text() 호출. text()는 내부 _messageQueue에 push하는데, ESPAsyncWebServer 소스 상 이 큐에 명시적 락이 없는 것으로 보임. async_tcp이 동시에 pop 중이면 std::list 손상 위험.

· 현재 메시지율(채널별 0.5~1.5s)이 낮아 실충돌 확률 낮음
· 권장: T-loop → T-async 전용 큐 → async_tcp에서 text() 호출, 또는 ESPAsyncWebServer의 락 문서 확인

[A-2] Gemini 프록시 블로킹

routeGeminiProxy → W10_callGeminiApi가 최대 15초간 async_tcp 태스크를 점유. WiFiClientSecure의 readBytes/readBytesUntil은 내부적으로 available() 폴링이라 timeout(15s) 동안 다른 요청 처리 불가. 단일 사용자라면 수용 가능하나, 폴링 병행 시 UI 멈춤.

권장: Gemini 호출도 F-05/F-06처럼 T-loop 또는 별도 태스크로 위임.

[A-3] routeScan 블로킹
