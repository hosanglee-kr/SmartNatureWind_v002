## 1. 시스템 개요
- **프로젝트명**: Smart Nature Wind (Standalone Firmware v0200)
- **MCU**: ESP32-S3-N16R8 (16MB Flash, 8MB OPI PSRAM, dual-core Xtensa LX7 @ 240MHz)
- **프레임워크**: PlatformIO + Arduino-ESP32 (C++17 표준 `-std=gnu++17`)
- **파일시스템**: LittleFS (`data_dir = ./src/v0200/data_v0200`)
  - **웹 개발 원본**: `src/v0200/data_src_v0200/html_v3/` (분할 JS 모듈, HTML, CSS 등 개발 원본 보존)
  - **빌드 파이프라인**: `src/v0200/tools_0200/pio_gzip_0200.py` (PlatformIO Pre-build 훅을 통해 메인 8개 JS 모듈을 `P010_bundle_0200.js`로 단일 번들링 후 전 웹 에셋 Level 9 Gzip 사전 압축)
  - **스테이징 배포**: `src/v0200/data_v0200/html_v3/` (LittleFS 이미지 빌드 대상)
- **아키텍처**: Standalone 풀스택 임베디드 펌웨어 (비동기 REST API + WebSocket + 반응형 Web UI + Gzip 정적 웹 호스팅 + 실시간 바람 물리 시뮬레이터)

## 5. 통신 및 API 사양
- **REST API**: `/api/v001/*`
  - 인증: `X-API-Key` 헤더 (설정된 `system.security.apiKey`가 비어있으면 누구나 접근 가능)
  - 주요 경로: `/api/v001/state` (`control.pendingReload`, `control.lastReloadOk` 포함), `/control/*`, `/motion/*`, `/system`, `/wifi/*`, `/reload`, `/config/save`
- **WebSocket 채널**: `/ws/{log|state|chart|metrics|summary}` (쿼리 파라미터 `?apiKey=...` 지원)
- **OTA 펌웨어 업데이트**: `/api/v001/fwUpdate` (POST multipart/form-data, `Update.h` 스트리밍)
- **파일 업로드**: `/api/v001/fileUpload` (최대 2MB, 에러 및 크기 초과 발생 시 `safeAbort`를 통한 열린 파일 핸들 즉시 close 보장)
- **정적 웹 호스팅**:
  - `Accept-Encoding: gzip` 헤더 유무 검사 (HTTP RFC 7231 준수, 헤더 미보유 시 raw 원본 서빙)
  - `/html_v3/*` 전체 경로에 대한 regex 라우트 (`^/html_v3/.+`) 기반 사전 압축 `.gz` 우선 서빙
  - 메인 JS 단일 번들(`P010_bundle_0200.js`) 및 정적 MIME 자동 판별 (`W10_guessMime`)
  - 루트(`/`) fallback 시 메인 HTML 부재 상황에서 무한 리다이렉트 루프를 차단하고 404 진단 메시지 반환

### 5.1 설정 재적용(Reload) 정책 (I-2 반영)

**핵심 원칙**: `POST /api/v001/reload` 요청은 **디스크(LittleFS)에 저장된 파일 상태로 메모리를 전면 재로드**한다.  
따라서 디스크에 영구 저장(`POST /api/v001/config/save`)되지 않고 메모리에만 머물러 있는 in-flight patch는 **소실**된다.

**동작 흐름 (F-05 반영)**
```text
[T-async: async_tcp]
  POST /api/v001/reload 수신
  → CL_CT10_ControlManager::requestReload() 호출 (atomic compare_exchange_strong)
  → 202 Accepted {"result":"queued", "note":"Reload requested..."} 즉시 반환 (< 1ms)

[T-loop: loopTask / A00_run]
  다음 루프 주기 (≤ 10ms)
  → CL_CT10_ControlManager::consumePendingReload() 확인 (atomic exchange)
  → true일 경우 reloadAll() 실행:
      1. CL_C10_ConfigManager::loadAll(디스크 → v_new_root) [T-loop 전용 C10 mutex]
      2. s_rootSwapMux 스핀락 보호 하에 g_A20_config_root ↔ v_new_root 원자적 포인터 스왑
      3. CT10 내부 제어 상태 및 파라미터 리셋 (_pendingMotionSimApply = false 방어적 초기화)
      4. v_old_root는 queuePendingFree()로 등록되어 3초 grace period 경과 후 loopTask에서 안전 해제
      5. CL_W10_WebAPI::applySystemRuntimeFromConfig()로 런타임 시스템 반영
```

**사용자 및 클라이언트 유의사항 (필수 원칙)**
1. `POST /api/v001/motion`, `/system`, `/wifi/config` 등은 **메모리 patch만** 수행한다.
2. reload 이전에 **메모리 패치 내용을 디스크에 영구 보존하려면 반드시 `POST /api/v001/config/save`를 먼저 호출**해야 한다.
3. reload 완료 시점 확인:
   - **REST 폴링**: `GET /api/v001/state` → `control.pendingReload` 필드가 `true`에서 `false`로 전환되는 시점 관찰.
   - **성공/실패 판별**: `control.lastReloadOk` (`true`: 리로드 성공 또는 초기 정상, `false`: 파일 파싱/뮤텍스 획득 실패).
   - **WebSocket**: `/ws/state` 브로드캐스트 메시지에서 `control.pendingReload` 및 `control.lastReloadOk` 플래그의 변화 감지.
4. **연속 중복 요청 차단**: 이미 reload가 pending 상태일 때 재요청 시 **409 Conflict** (`{"error":"reload already pending"}`)를 즉시 반환한다.

**금지 패턴**:
```text
POST /motion (메모리 패치) ─┐
                             ├─ (100ms 이내 save 없이) → POST /reload  ← 패치가 디스크 원본으로 덮어써져 유실됨!
                            ─┘
```
→ 반드시 `POST /motion` → `POST /config/save` → `POST /reload` 순서를 준수해야 한다.

## 6. 코딩 및 품질 컨벤션
- **JSON 라이브러리**: ArduinoJson v7.x 전용 (`JsonDocument` 단일 할당, deprecated 함수 `containsKey`, `createNestedObject/Array` 사용 절대 금지).
- **문자열 안전성**: `memset` 초기화 후 `strlcpy` 또는 `A25_Com_Utils`의 안전 복사 함수 강제 사용 (Buffer Overflow 방지).
- **식별자 네이밍**:
  - 전역 상수: `G_`, 전역 변수: `g_`
  - 클래스: `CL_`, 구조체: `ST_..._t`, Enum: `EN_`
  - 지역 변수: `v_`, 매개변수: `p_`, 정적 멤버: `s_`, 비공개 멤버: `_`
- **시스템 로깅**: `CL_D10_Logger::log(EN_L10_LOG_*, "[모듈] 메시지", ...)` 표준 규격 사용.
