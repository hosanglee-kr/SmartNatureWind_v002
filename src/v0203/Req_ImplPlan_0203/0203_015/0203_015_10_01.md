## 1. 현황 및 문제 정의

### 1.1 현재 구조
* **백엔드 (`src/v0203/W10_Web_Gemini_0203.cpp`, `W10_Web_0203.h`)**
  * `routeGeminiProxy()`가 `ESPAsyncWebServer`의 `async_tcp` 컨텍스트에서 요청 바디를 누적한 뒤 `handleGeminiProxy()`를 동기 호출합니다.
  * `handleGeminiProxy()` 내부에서 Turn 1 JSON 조립, `W10_callGeminiApi()` (`WiFiClientSecure` + `HTTPClient`, `Connection: close`, 타임아웃 `G_GEMINI_TIMEOUT_MS = 20000 ms`) 호출, `CT10_AI::executeAIAction()` 실행, 필요 시 Turn 2 `W10_callGeminiApi()` 호출 후 `sendJson(..., 200)`으로 응답합니다.
  * `W10_getGeminiApiKey()`는 `async_tcp` 단일 태스크 실행을 전제로 `static char s_keyBuf[64]`를 사용합니다.
* **프론트엔드 (`src/v0203/data_v0203_src/html_v0203/js/core/040.api.js`, `010.config.js`)**
  * `SNW.Api.gemini(body)`가 `TIMEOUT_MS.GEMINI = 45000` (45초) 설정으로 단일 `POST` 요청을 대기합니다.

### 1.2 실측 데이터 (`esp32-s3-zero`, `gemini-3.5-flash-lite` + 1-turn 제어 최적화 기준)
* **지연 시간**
  * 1-turn 제어 명령 (`"바다바람 5분"`, `bodyLen=4314`):
    * 백엔드 `[AI_PROF]`: `bodyLen=4314 code=200 beginMs=1 postMs=1991 readMs=6 totalMs=1998` (**~2.0초**)
    * 클라이언트(PowerShell) 총 RTT: **3,848 ms**
    * 브라우저 DOM 배지 렌더(`#/ai`): **4,834 ms**
  * 2-turn 조회(`get_status`, `list_profiles`, `list_schedules`) 또는 네트워크 지연 시: `W10_callGeminiApi()` 2회 직렬 호출로 **4~6초**, 타임아웃 시 **최대 20~40초**까지 `async_tcp` 점유 가능.
* **메모리 및 태스크 현황 (`CONTRACT_0203.md` 및 실측)**
  * 정적 RAM: `30.8%` (`100,976 / 327,680 B`), Flash: `43.8%` (`1,378,713 / 3,145,728 B`)
  * 가용 내부 SRAM (`MALLOC_CAP_INTERNAL`): `177,304 B` (~173 KB) *(디버그 빌드 기준 실측)*
  * 가용 PSRAM (`MALLOC_CAP_SPIRAM`): `1,939,527 B` (~1.85 MB) *(디버그 빌드 기준 실측)*
  * 주요 상주 태스크: `loopTask` (`8,192 B`), `async_tcp` (`4,096 B`), `WF10_Reconnect` (`8,192 B`), `dht_task` (`3,072 B`, Core 1), `sys_evt` (`3,584 B`)

### 1.3 핵심 제약 사항
1. **`async_tcp` 블로킹 영향**: `async_tcp`는 모든 HTTP 요청 및 WebSocket(`/ws/log` 등) 이벤트를 처리하므로, Gemini 응답 대기 중 다른 UI 조작·폴링·실시간 로그 푸시가 정지됩니다.
2. **`ESPAsyncWebServer` 비스레드 안전성**: 백그라운드 태스크가 `AsyncWebServerRequest*`를 보관했다가 나중에 `send()`를 호출하면, 그 사이 클라이언트가 연결을 끊었을 때 `LoadProhibited` (UAF) 크래시가 발생할 수 있습니다.
3. **일회성 태스크 종료 시 누수 위험**: `vTaskDelete(NULL)`를 C++ RAII 객체(`String`, `JsonDocument`, `WiFiClientSecure`)와 같은 스코프에서 호출하면 소멸자가 실행되지 않아 힙이 누수됩니다.
4. **보안 원칙 (`.agents/rules/security.md`)**: 브라우저 직접 호출 방식은 Gemini API 키가 클라이언트에 노출되므로 불가합니다.

## 2. 아키텍처 대안 비교

| 구분 | 방안 A: 상주 워커 + `202` 폴링 **(선정)** | 방안 B: 일회성 태스크 + `202` 폴링 | 방안 D: 상주 워커 + WebSocket 푸시 | 방안 E: 현행 동기 `200 OK` 유지 |
|---|---|---|---|---|
| **동작 방식** | `gemini_worker` 1개 상주 + 1슬롯 Job 처리, `POST` 즉시 `202 {jobId}`, `GET ?jobId=...` 폴링 | 요청 시 `xTaskCreate` 생성, 내부 스코프 종료 후 `vTaskDelete(NULL)`, `202` + 폴링 | 워커 처리는 A와 동일, 결과만 WebSocket으로 푸시 | `async_tcp` 내부에서 동기 `W10_callGeminiApi()` 유지 |
| **`async_tcp` 블로킹** | **~0 ms** (완전 해소) | **~0 ms** (완전 해소) | **~0 ms** (완전 해소) | **~2.0초** (2-turn·지연 시 4~20초+) |
| **메모리 특성** | 워커 스택 **8~10 KB** 상시 점유, 힙 단편화 없음 | 평소 0 B, 실행 중 8~10 KB (반복 생성/해제 시 단편화 위험) | A와 동일 (8~10 KB 상시 점유) | 추가 스택 0 B |
| **안전성·구현성** | `s_keyBuf` 워커 전용화, 단일 슬롯 직렬화(`429`) 용이 | RAII 소멸자 누수 방지 스코프 분리 필수 | WS 재접속·모바일 백그라운드 유실 대비 폴백 폴링 필요(이중 경로) | 코드/계약 변경 없음 |
| **문서·E2E 영향** | 계약 6종 + `040.api.js` + E2E 수정 | A와 동일 | A + WS 이벤트 스키마 추가 | 없음 |

* **선정 사유**: `async_tcp` 블로킹을 근본 제거하면서도 힙 단편화(`B`의 단점)와 이벤트 유실 복구 복잡도(`D`의 단점)를 피할 수 있는 **방안 A**가 가장 균형 잡힌 해법입니다.

## 3. 방안 A 추가 최적화 설계 (5대 개선 포인트)

방안 A 도입 시 현재 `W10_Web_Gemini_0203.cpp`와 `040.api.js`의 구조적 비효율을 함께 개선합니다.

### 3.1 `async_tcp` 부담 제로화 (파싱·조립까지 워커로 이관)
* **현재**: `async_tcp`가 JSON 파싱(`p_inDoc`) 및 요청 조립까지 관여.
* **개선**: `async_tcp`는 아래 최소 검증만 수행하고 즉시 `202 Accepted`를 반환합니다.
  1. `requireApiKey()` 인증 확인
  2. 바디 크기(`<= 12 KB`) 및 비어 있지 않음 확인
  3. 워커 상태 확인 (`RUNNING` 중이면 즉시 `429 {"error":"ai_busy"}`)
  4. raw JSON 바디를 Job 버퍼로 복사 후 워커 시그널(`xTaskNotify` / 세마포어) 전송
* `deserializeJson()` 및 Turn 1/2 요청 조립은 모두 `gemini_worker` 내부에서 수행하여 `async_tcp`(`4,096 B` 스택)의 CPU·스택·힙 피크를 제거합니다.

### 3.2 `handleGeminiProxy` 내부 `JsonDocument` 및 프롬프트 중복 제거
* **현재 (`W10_Web_Gemini_0203.cpp` L240~L288)**: Turn 2가 필요 없는 일반 제어 명령에서도 `v_turn2Req`를 미리 선언하고 `CT10_AI::buildAIPromptStrict()` 호출 및 `v_contents` 복사를 먼저 수행합니다.
* **개선**:
  1. **Turn 2 지연 생성(Lazy Init)**: `v_needTurn2 == true`가 확정된 블록 내부에서만 `v_turn2Req`를 생성하고 `buildAIPromptStrict()`를 호출합니다.
  2. **수명 조기 종료**: `v_t1Body` 직렬화 완료 후 Turn 2가 불필요하다면 `v_turn1Req`를 즉시 `.clear()`하거나 스코프를 닫아, **TLS 핸드셰이크(~35 KB 힙 점유) 시점의 동시 힙 피크**를 낮춥니다.

### 3.3 워커 메모리 및 락 경계 최적화 (내부 SRAM 보호)
* **스택 vs 대용량 버퍼 분리**:
  * `gemini_worker` 태스크 스택(`8,192~10,240 B`)은 mbedTLS/Wi-Fi 안전성을 위해 내부 SRAM에 배치합니다.
  * 1슬롯 Job 컨텍스트의 대용량 버퍼(요청 바디 최대 `12 KB`, 응답 JSON 최대 `8 KB`)는 `MALLOC_CAP_SPIRAM` (PSRAM, 가용 `~1.85 MB`)에 할당해 내부 SRAM(`~173 KB`) 여유를 보호합니다.
* **정적 버퍼 정리**: `W10_getGeminiApiKey()`의 `s_keyBuf[64]`는 워커 전용으로 제한(또는 워커 시작 시 1회 로드)하여 다중 태스크 경합을 제거합니다.
* **단일 슬롯 직렬화**: `RUNNING` 중 중복 `POST`는 `429`로 즉시 거절하여 기존 `G_RATE_LIMIT_MS(5000 ms)` 정책과 자연스럽게 통합합니다.

### 3.4 프론트엔드(`040.api.js`) 투명 래핑 및 적응형 폴링
* **호출부 무변경 호환**:
  * `SNW.Api.gemini(body)` 내부에서 `res.status === 202`를 감지하면 `GET /api/v001/ai/gemini?jobId=...` 폴링을 자동 수행한 뒤 최종 JSON을 반환합니다.
  * `200 OK` 응답 시에는 즉시 반환하도록 분기해 과도기 호환성을 확보합니다.
* **적응형 폴링(Adaptive Polling)**:
  * 실측 1-turn 소요 시간이 `~2.0초`이므로 초기 과다 폴링을 피합니다.
  * `POST` 직후 **첫 폴링은 `700 ms` 대기**, 이후 완료될 때까지 **`350 ms` 간격**으로 조회하여 불필요한 HTTP 왕복을 줄이면서 추가 체감 지연을 최소화합니다.
* **Job 결과 수명(TTL)**:
  * 클라이언트가 탭을 닫거나 `TIMEOUT_MS.GEMINI(45초)` 타임아웃으로 폴링을 중단해도 슬롯이 고착되지 않도록, 완료(`DONE`/`ERROR`) 상태는 **TTL(예: 30초) 경과 또는 다음 `POST` 수신 시 자동 폐기/덮어쓰기**합니다.

### 3.5 관측성(`AI_PROF`) 구간 분리 로깅
* 기존 `[AI_PROF]` 로그에 아래 세부 구간 타이밍을 추가해 병목 분리를 상시화합니다.
  * `queueWaitMs` (요청 접수 → 워커 착수)
  * `turn1Ms` (Turn 1 조립 + Gemini HTTP 왕복)
  * `actionMs` (`executeAIAction` 실행)
  * `turn2Ms` (Turn 2 발생 시)
