## 1. 목적 및 설계 원칙

### 1.1 목적
- 백엔드 제공 기능(v0201 REST API 및 WebSocket)으로 완결되는 프론트엔드 기능 요구사항 정의
- 4개 사용자 역할(L1~L4)에 따른 계층적 접근 권한 및 UI 복잡도 제어
- 페이지별 API/WS 매핑 확정 및 Dashboard L1 MVP 화면 설계 통합

### 1.2 설계 원칙
1. **백엔드 계약 우선 (Contract First)**: API/WS 미지원 기능은 "Gap"으로 명시하며, 백엔드 계약을 임의로 우회하지 않는다.
2. **역할 기반 점진적 노출 (Progressive Disclosure)**: L1(초보)에게는 필수 조작만, L4(엔지니어)에게는 시스템 전체 제어권을 노출한다.
3. **Stateless 클라이언트**: 인증은 `X-API-Key` 헤더와 WS 쿼리 파라미터만 사용하며 세션 유지는 로컬스토리지에 위임한다.
4. **WS 우선, REST 폴백 (WS-First, REST-Fallback)**: 실시간 상태 반영은 WebSocket 3개 채널을 최우선으로 하고, 연결 실패 시 지수 백오프 기반 REST 폴링으로 전환한다.
5. **Save → Reload 순서 강제**: 시스템/모션/네트워크 설정 수정 시 반드시 `PATCH/POST` → `POST /config/save` → `POST /reload` 순서를 준수한다.

## 5. 페이지별 핵심 기능 요구사항

### 5.1 Dashboard (제어 메인)
- **접근**: L1~L4 전 계층 / **목적**: 기기 상태 모니터링 및 즉시 팬 제어
- L1: 전원 On/Off, 10종 프리셋 원클릭 선택, 0~100 강도 슬라이더, 상태/센서 요약 카드
- L2+: 스타일 선택 및 미세 조정(variability, gustFreq, fanLimit, minFan), Override 제어, 10초 미니 차트
- L3+: FSM 상태/이유 툴팁, AutoOff 상태 배지 및 이벤트 ACK
- L4: `pendingReload`, `lastReloadOk` 등 리로드 모니터링
- *(상세 스펙은 [§6 Dashboard 메인 제어 상세 스펙](#6-dashboard-메인-제어-상세-스펙) 참조)*

### 5.2 Preset & Style Explorer
- **접근**: L2~L4 / **목적**: 10종 프리셋 및 5종 스타일 탐색 및 커스터마이징
- 프리셋별 14개 물리 인자(기저 풍속, 난류 강도, 돌풍 주기 등) 시각화 및 원클릭 즉시 적용
- L3+: 프리셋 CRUD (최대 10개, styles 5종은 고정)
- L4: 14개 factors 전량 세밀 편집

### 5.3 Live Chart
- **접근**: L2~L4 / **목적**: WebSocket 기반 실시간 물리 곡선 모니터링
- 120초 다중선 실시간 렌더링 (풍속, 목표 풍속, PWM 출력, 난류/열기포 이벤트 마커)
- L3+: PWM 오버레이 토글, 시간축 변경 (5초/30초/120초), CSV 내보내기
- L4: S10 물리 엔진 내부 상태 관측

### 5.4 Scheduler
- **접근**: L2~L4 / **목적**: 요일/시간대별 자동 운전 스케줄링
- 주간 8개 스케줄 목록 표시 및 활성화 토글, 세그먼트 시각화
- L3+: 스케줄 CRUD, 요일별 반복, AutoOff/모션 연동 설정
- **제약**: `schId`/`segId`는 서버 자동 발급(요청값 무시), `schNo`/`segNo`는 사용자 지정, 중복 검증은 save 시점에 수행

### 5.5 User Profiles
- **접근**: L2~L4 / **목적**: 개인화 맞춤 프로필 관리
- 최대 6개 프로필 목록 및 원클릭 시작/정지 (`/control/profile/{select,stop}`)
- L3+: 프로필 CRUD 및 세그먼트 편집
- L4: 일괄 패치 (`POST /user_profiles/patch`)

### 5.6 Sensors & Motion
- **접근**: L2~L4 / **목적**: DHT22 온습도 및 PIR 인체감지 센서 연동
- 실시간 온습도 및 재실 여부 표시, 모션 유지 시간(`holdSec`) 카운트다운
- L3+: PIR 지연시간 및 DHT22 오프셋 보정, 가상 PIR 피드 테스트
- L4: 원시 센서값 및 디바운스 파라미터 제어

### 5.7 System Settings
- **접근**: L3~L4 / **목적**: 시스템 전반 환경설정
- 로그 레벨/버퍼 크기, WS 채널 주기, 시간대(Timezone), NTP 서버 설정, API Key 변경
- L4: 하드웨어 GPIO 핀맵(PWM/DHT/PIR/LED), 팬 커브 4구간 설정, 공장 초기화 및 기기 재부팅

### 5.8 Network & Time
- **접근**: L3~L4 / **목적**: Wi-Fi 및 시간 동기화 관리
- SoftAP(`NatureWind`/`2540`) 설정 및 STA 접속 상태, 주변 Wi-Fi 스캔 및 접속
- NTP 서버 3중 폴백 관리 및 SNTP 동기화 상태 점검
- L4: Wi-Fi 재연결 이벤트 로그 및 TM10 내부 상태

### 5.9 Logs
- **접근**: L3~L4 / **목적**: 실시간 링버퍼 로그 확인
- 최대 256개 링버퍼 로그 조회 및 레벨(ERROR/WARN/INFO/DEBUG) 필터링
- `/ws/log` WebSocket 실시간 스트리밍
- L4: 모듈별 필터 및 JSON 파일 다운로드

### 5.10 Diagnostics
- **접근**: L4 전용 / **목적**: 시스템 런타임/메모리/동시성 심층 진단
- Free Heap/PSRAM/LittleFS 실측치, FSM 내부 상태코드 및 reasonCode 확인
- AutoOff 3종 런타임 트리거, NVS 누적 운전 통계, Dirty Flag 현황, API 버전 4종 확인

### 5.11 Firmware
- **접근**: L4 전용 / **목적**: 무선 OTA 펌웨어 업데이트 및 에셋 관리
- 현재 SemVer 확인 및 펌웨어 바이너리 멀티파트 업로드 (자동 재부팅)
- LittleFS 웹 에셋 및 설정 JSON 직접 업로드

### 5.12 AI Assistant (선택 기능)
- **접근**: L4 전용 / **목적**: Google Gemini 연동 자연어 기기 제어
- 자연어 질의를 통한 상태 진단, 최적 프리셋 추천, 설정 생성 지원 (Rate limit 3초)

## 6. Dashboard 메인 제어 상세 스펙

### 6.1 사용자 흐름

#### L1 흐름 (기본 제어)
```text
[부팅/접속] → GET /state (초기 스냅샷) → WS 3채널 병렬 연결
        │
        ├─→ [전원 On/Off 토글] → POST /control/override/fixed (forever=true) 또는 /override/clear
        ├─→ [프리셋 10개 선택] → POST /simulation (patch: presetCode, styleCode)
        └─→ [강도 조절 0~100]  → POST /simulation (patch: intensity, 디바운스 300ms)
                                    ↓
                        WS /ws/state 실시간 갱신 (800ms) → UI 즉각 반영
```

#### L2~L4 확장 흐름 (세부 제어)
```text
[스타일/물리인자 조정] → POST /simulation (patch: styleCode, variability, gustFreq, fanLimit, minFan)
[정밀 Override]        → POST /control/override/{fixed, preset, clear}
[실시간 미니차트]      → WS /ws/chart (diffOnly 최신 데이터 구독)
[FSM 진단]             → GET /state (.control.state, reason, runSource)
```

### 6.2 상태 필드 → UI 요소 매핑

#### 6.2.1 `GET /state` 응답 매핑
*백엔드 `exportStateJson_v02` 규격 준수*

| 응답 필드 | UI 컴포넌트 | L1 | L2 | L3 | L4 |
|---|---|:---:|:---:|:---:|:---:|
| `control.active` | 전원 상태 배지 ("작동 중" / "대기 중") | ✅ | ✅ | ✅ | ✅ |
| `control.profileMode` | 프로필 모드 활성 표시 | ❌ | ✅ | ✅ | ✅ |
| `control.state` (문자열) | FSM 상태 아이콘 및 색상 배지 | ❌ | ❌ | ✅ | ✅ |
| `control.stateCode` | FSM 상태 코드 수치 표기 | ❌ | ❌ | ❌ | ✅ |

|---|:---:|:---:|---|

### 6.5 UX 세부 규칙

#### 6.5.1 초기 로딩 시퀀스
```text
1. [L4만] GET /version (펌웨어 버전 및 해시 확인)
2. [전체] GET /state (초기 상태 스냅샷 즉시 렌더링)
3. [병렬 연결] WebSocket:
   - /ws/state?apiKey=... (메인 상태)
   - /ws/summary?apiKey=... (요약 정보)
   - /ws/metrics?apiKey=... (메트릭)
4. [L2+] /ws/chart?apiKey=... (미니 차트 구독)
5. [L3+] /ws/log?apiKey=... (로그 스트림)
```

#### 6.5.2 통신 에러 처리
| 에러 상황 | 원인 | 프론트엔드 대응 |
|---|---|---|
| `401 Unauthorized` | API Key 불일치 또는 미입력 | API Key 입력 모달 팝업 표시 |
| `409 Conflict` | 이미 Reload 진행 중 | "설정 재로드가 진행 중입니다" 토스트 알림 |
| `500 Internal Error` | 부팅 초기화 미완료 | 10초 카운트다운 후 자동 재시도 안내 |
| WS 연결 끊김 | 네트워크 단절 또는 재부팅 | 상단 헤더에 "오프라인" 표시 후 지수 백오프 재연결 시도 |
| `updated: false` | 변경 사항 없음 또는 유효성 실패 | "변경 사항이 없거나 유효하지 않습니다" 메시지 표시 |

#### 6.5.3 휘발성 제어 원칙 (Save → Reload 금지)
- Dashboard에서 수행하는 `POST /simulation` 및 `POST /control/override/*` 조작은 **휘발성 런타임 제어**이다.
- Dashboard에서 조작 즉시 `POST /config/save`를 자동 호출하는 것을 **엄격히 금지**한다 (플래시 마모 방지 및 실시간성 보장).
- 영구 보존이 필요한 경우 사용자가 명시적으로 상단 "설정 저장" 버튼을 눌러 수행한다.

#### 6.5.4 과냉 방지 AutoOff 연동
- 센서 온도(`control.sensor.tempC`)가 설정된 최저 안전 온도(`offTemp`)에 도달하면 즉시 "과냉 방지 자동 정지" 경고 배지를 점등한다.

## 8. 백엔드 Gap 분석 및 프론트엔드 대응 전략

|:---:|---|---|
| 1 | **Temp-Auto 모드 미구현** | UI 모드 선택 목록에서 제외하거나 "준비 중" 비활성 배지로 처리 |
| 2 | **세션 기반 로그인 없음 (API Key만 지원)** | 브라우저 `localStorage`에 API Key를 저장하고 매 요청 헤더/쿼리에 자동 주입 |
| 3 | **Style 수정 API 미제공** | Style은 5개 고정 옵션으로만 제공하고, Preset만 CRUD 편집 기능 노출 |
| 4 | **스케줄 중복 사전 검증 API 부재** | 프론트엔드에서 1차 시간대 겹침 검증 수행 후 저장(Save) 응답 결과로 최종 처리 |

| 7 | **자동 백업/복원 관리 미지원** | 브라우저에서 JSON 파일 업로드(`POST /fileUpload`) 인터페이스로 우회 구현 |
| 8 | **서버 주도 WS 재연결 핸드셰이크 없음** | 클라이언트 측에서 exponential backoff 재연결 루프 전담 구현 |

## 10. 계약 준수 사항 및 개발 가이드라인

1. **API 인증 헤더**: 모든 REST 엔드포인트 호출 시 `X-API-Key` 헤더를 반드시 포함한다 (키가 비어있는 개발 모드에서도 빈 헤더 전송).
2. **WebSocket 연결 규격**: 모든 WS 핸드셰이크 요청 URL에 `?apiKey=...` 쿼리 파라미터를 명시한다.
3. **Save → Reload 순서 보장**: `/system`, `/motion`, `/wifi/config` 등 영구 설정 패치 후 반드시 `POST /config/save` → `POST /reload` 순서로 호출하며, save 없이 reload를 호출하는 금지 패턴을 엄격히 방지한다.
4. **재로드 상태 감시**: Reload 요청 후 `control.pendingReload`가 `true`에서 `false`로 전이될 때까지 폴링하고, `control.lastReloadOk`를 확인하여 성공 여부를 사용자에게 고지한다.
5. **시간 규격 준수**: 모든 시간 필드는 epoch 밀리초(`epochms`) 단위를 사용하며, 기기의 SNTP 시간 동기화(`control.time.valid == true`)가 완료된 이후에만 유효한 값으로 취급한다.
6. **에러 응답 규격**: 백엔드의 표준 오류 응답 형식인 `{"error": "<원인 메시지>"}` 구조를 파싱하여 토스트 또는 경고창으로 일관되게 렌더링한다.
