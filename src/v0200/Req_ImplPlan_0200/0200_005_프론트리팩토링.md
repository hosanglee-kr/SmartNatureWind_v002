## 1. 목적 및 설계 원칙

### 1.1 목적
- 백엔드 제공 기능으로 구현 가능한 프론트엔드 요구사항 정의
- 4개 사용자 역할별 접근 범위 명시
- 페이지별 API/WS 매핑 및 기능 우선순위 확정

### 1.2 설계 원칙
1. **백엔드 계약 우선**: API/WS 미지원 기능은 "Gap"으로 명시, 프론트엔드 대응 정의
2. **역할 기반 접근**: L1(일반) → L4(엔지니어) 계층적 노출
3. **Stateless 클라이언트**: 사용자 인증은 `X-API-Key`만 (백엔드 세션 없음)
4. **WS 우선, REST 폴백**: 실시간성은 WS, 초기값/폴링은 REST
5. **Save→Reload 순서 강제**: system/motion/wifi patch 후 반드시 `POST /config/save` → `POST /reload`

## 5. 백엔드 Gap 및 프론트엔드 대응

| Gap | 프론트엔드 대응 |
|---|---|
| Temp-Auto 모드 미실 구현 | "준비 중" 표시 또는 메뉴 숨김 |
| 사용자 로그인 없음 (X-API-Key만) | localStorage API Key, 자동 헤더 |
| styles 편집 API 없음 | preset CRUD만 노출 |
| Scheduler dry-run 없음 | 저장 응답으로만 판단 |
| timezone 목록 API 없음 | 자유 텍스트 + 프리셋(Asia/Seoul 등) |
| 파일 다운로드 API 없음 | `GET /config`로 JSON export |
| 백업/복원 미지원 | 파일 업로드로 우회 |
| WS 재연결 정책 없음 | 클라이언트 exponential backoff |
| 세션 만료 없음 | API Key 재입력 유도 |
| OTA 진행률 서버 API 없음 | fetch progress event |

## 6. 구현 우선순위

| Phase | 대상 Level | 페이지 | 예상 |
|:---:|:---:|---|:---:|
| **P1** | L1 | Dashboard (기본) | MVP |
| **P2** | L2 | Preset Explorer + Live Chart + Scheduler + User Profiles + Sensors | 확장 |
| **P3** | L3 | System Settings + Network & Time + Logs | 관리 |
| **P4** | L4 | Diagnostics + Firmware + AI Assistant (선택) | 엔지니어 |

**필수 Save→Reload 순서**: system/motion/wifi patch → `POST /config/save` → `POST /reload` (SPEC §5.2)

**금지 패턴**: patch 후 save 없이 reload → 패치 유실.

## 7. 계약 준수 사항

| 항목 | 준수 |
|---|---|
| API 인증 | `X-API-Key` 헤더 (비어있으면 개방) |
| WS 인증 | `/ws/*?apiKey=...` 쿼리 |
| Save→Reload | 반드시 순서 준수 (SPEC §5.2) |
| 재로드 폴링 | `control.pendingReload` true→false, `control.lastReloadOk`로 성공 판별 |
| 에러 응답 | `{"error":"..."}` 표준 준수 |
| 시간 필드 | epochms (SNTP sync 후만 유효) |
| WS 재연결 | 클라이언트 exponential backoff (1s→2s→4s→…30s) |
