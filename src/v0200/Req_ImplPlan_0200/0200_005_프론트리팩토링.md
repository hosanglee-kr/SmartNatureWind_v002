# FRONTEND_REQ_0200.md — 프론트엔드 요구사항 정의서

> **SSOT**: 본 문서는 v0201 백엔드 API/WS 계약을 기반으로 프론트엔드 요구사항을 정의한다.  
> **준수 대상**: `SPEC_0200.md` §5 (API), `CONTRACT_0200.md` §4 (태스크 경계/위임).  
> **파일명 정책**: 계약 문서 `_0200.md` 유지, 코드 참조 `_0201` 접미사.  
> **범위**: 기존 프론트엔드 미고려, 원점 재검토. 백엔드 제공 기능만 사용.

---

## 1. 목적 및 설계 원칙

### 1.1 목적
- 백엔드 제공 기능으로 구현 가능한 프론트엔드 요구사항 정의
- 4개 사용자 역할별 접근 범위 명시
- 페이지별 API/WS 매핑 및 기능 우선순위 확정

### 1.2 설계 원칙
1. **백엔드 계약 우선**: API/WS 미지원 기능은 "Gap"으로 명시, 프론트엔드 대응 정의
2. **역할 기반 접근**: L1(일반) → L4(엔지니어) 계층적 노출
3. **Stateless 클라이언트**: 사용자 인증은 `X-API-Key`만 (백엔드 세션 없음)
4. **WS 우선, REST 폴백**: 실시간성은 WS, 초기값/폴링은 REST
5. **Save→Reload 순서 강제**: system/motion/wifi patch 후 반드시 `POST /config/save` → `POST /reload`

## 5. 백엔드 Gap 및 프론트엔드 대응

| Gap | 프론트엔드 대응 |
|---|---|
| Temp-Auto 모드 미실 구현 | "준비 중" 표시 또는 메뉴 숨김 |
| 사용자 로그인 없음 (X-API-Key만) | localStorage API Key, 자동 헤더 |
| styles 편집 API 없음 | preset CRUD만 노출 |
| Scheduler dry-run 없음 | 저장 응답으로만 판단 |
| timezone 목록 API 없음 | 자유 텍스트 + 프리셋(Asia/Seoul 등) |
| 파일 다운로드 API 없음 | `GET /config`로 JSON export |
| 백업/복원 미지원 | 파일 업로드로 우회 |
| WS 재연결 정책 없음 | 클라이언트 exponential backoff |
| 세션 만료 없음 | API Key 재입력 유도 |
| OTA 진행률 서버 API 없음 | fetch progress event |

## §9. Dashboard 상세 스펙

### 9.1 페이지 목적 및 사용자 흐름

**목적**: 팬 제어의 단일 진입점. 상태 조회 + 즉시 제어.

**L1 흐름**:
```
[부팅/접속] → GET /state (초기 스냅샷) → WS 3채널 연결
        │
        ├─→ [On/Off 토글] → POST /control/override/fixed (forever=true) or /override/clear
        ├─→ [프리셋 선택] → POST /simulation (patch: presetCode/styleCode)
        └─→ [강도 조절]   → POST /simulation (patch: intensity)
                                    ↓
                        WS /ws/state 실시간 갱신 → UI 반영
```

**L2~L4 추가 흐름**:
```
[스타일/변수 조정] → POST /simulation (patch: styleCode/variability/gustFreq/fanLimit/minFan)
[Override 선택]    → POST /control/override/{fixed,preset,clear}
[미니차트]          → WS /ws/chart (diffOnly 최신 1개)
[FSM 진단]          → GET /state (.control.state/reason/runSource)
```

### 9.4 CT10 7-State FSM → UI 표시

| stateCode | state | 아이콘 | 색상 | 표시 텍스트 | L1 | L2 | L3 | L4 |
|:---:|---|---|:---:|---|:---:|:---:|:---:|:---:|
| 0 | `IDLE` | ⏸ | 회색 | "대기 중" | ✅ | ✅ | ✅ | ✅ |
| 1 | `OVERRIDE` | ✋ | 파랑 | "수동 제어 중" | ✅ | ✅ | ✅ | ✅ |
| 2 | `PROFILE_RUN` | 👤 | 초록 | "프로파일 실행 중" | ❌ | ✅ | ✅ | ✅ |
| 3 | `SCHEDULE_RUN` | 📅 | 청록 | "스케줄 실행 중" | ❌ | ✅ | ✅ | ✅ |
| 4 | `MOTION_BLOCKED` | 🚫 | 노랑 | "인체 미감지" | ✅ | ✅ | ✅ | ✅ |
| 5 | `AUTOOFF_STOPPED` | ⏹ | 주황 | "자동 꺼짐" | ✅ | ✅ | ✅ | ✅ |
| 6 | `TIME_INVALID` | 🕐 | 빨강 | "시간 미동기" | ❌ | ✅ | ✅ | ✅ |

**reasonCode 툴팁** (L3~L4): `NONE/OVERRIDE_ACTIVE/PROFILE_MODE/USER_PROFILE_ACTIVE/SCHEDULE_ACTIVE/NO_ACTIVE_SCHEDULE/NO_SCHEDULES/TIME_NOT_VALID/MOTION_NO_PRESENCE/AUTOOFF_{TIMER,TIME,TEMP}`

**이벤트 ACK**: `AUTOOFF_STOPPED` 상태에서 `event.ackRequired=true` 또는 `holdRemainMs>0` 표시. 사용자가 "확인" 버튼 클릭 → `POST /state` 폴링으로 `holdRemainMs=0` 확인 후 UI 정상화.

### 9.5 UX 세부 규칙

#### 9.5.1 초기 로드 순서
```
1. GET /version          (버전 확인, L4만)
2. GET /state            (초기 스냅샷)
3. WS 연결 병렬:
   - /ws/state?apiKey=...
   - /ws/summary?apiKey=...
   - /ws/metrics?apiKey=...
4. (L2+) WS /ws/chart 연결
5. (L3+) WS /ws/log 연결
```

#### 9.5.2 에러 처리
| 에러 | 원인 | 대응 |
|---|---|---|
| `401 unauthorized` | API Key 불일치 | API Key 재입력 모달 |
| `409 reload already pending` | 중복 reload | "이미 재로드 중" 토스트 |
| `500 control not ready` | 부팅 미완료 | 10초 후 자동 재시도 |
| WS 연결 끊김 | 네트워크/기기 재부팅 | exponential backoff 재연결 |
| `updated: false` (POST /simulation) | 값 무변경 또는 검증 실패 | "변경 사항 없음" 또는 필드 검증 오류 표시 |

#### 9.5.3 Save→Reload 금지 패턴 (L3~L4)
- Dashboard에서 `POST /simulation` 후 **`POST /config/save` 자동 호출 금지**
- Dashboard는 **휘발성 제어**만 담당, 영구 저장은 System Settings에서 명시적 수행

#### 9.5.4 온도 AutoOff (L3~L4)
- `control.sensor.tempC` ≥ AutoOff 임계 온도 시 "곧 자동 꺼짐" 경고 배지
- 임계값은 `control.autoOffRt.offTemp` 표시
