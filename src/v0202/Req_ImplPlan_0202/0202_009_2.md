1️⃣ 첫 만남 — 개봉 ~ 전원 인가

😕 불편했던 순간

"설명서가 없네?"

· 박스에 제품, 전원 어댑터, 짧은 안내 카드 1장만 있음
· 안내 카드에 "Wi-Fi: NatureWind / 비번: 2540 / http://192.168.4.1" — 이거 하나로 끝
· 근데 "이 제품이 뭘 할 수 있는지" 아무 설명 없음
· 앱스토어 앱도 없고, QR코드도 없음 → "내 폰에 뭘 설치해야 하지?" 10분간 헤맴

"전원은 어디에?"

· 몸체에 물리 버튼이 하나도 없음
· 어댑터 꽂았더니 LED가 파란색/초록색으로 깜빡임 → "이게 정상인가?" 불안
· 팬이 안 돌아서 "불량인가?" 의심 → 30분간 재포장 고민

"이 제품 팬이 어디에 있지?"

· 팬이 몸체 내부에 있어서 겉으론 잘 안 보임 → 설명서 없이는 조립 방향도 모름

💡 개선 제안 (우선순위 中)

1. QR 코드 카드 필수: 박스에 3초 안내 QR (스마트폰 카메라로 찍으면 자동 접속)
2. 첫 부팅 안내 LED: 파란/녹색 깜빡임 = "Wi-Fi 대기 중"을 안내 카드에 큰 그림으로
3. 물리 ON/OFF 버튼 1개: 스마트폰 없는 손님, 재난 상황 대비 (현재 아예 없음)
4. 미니 브로셔: "이 제품은 10가지 자연풍을 재현합니다" A4 1장

2️⃣ Wi-Fi 연결 — 첫 관문

😕 불편했던 순간

"인터넷 끊겼다고 경고가 떠요"

```
[iPhone] "NatureWind"에 연결됨
         인터넷 연결 없음
         [연결 유지] [Wi-Fi 전환]
```

· 매번 "연결 유지" 눌러야 함
· 아내 폰(안드로이드)은 자동으로 LTE로 전환되어 접속 안 됨 → 원인 몰라 30분 헤맴

"192.168.4.1... 외우기 어려움"

· QR 코드나 앱이 없어서 주소를 매번 검색해서 찾아야 함
· 홈 화면에 바로가기 추가했지만 아이콘 없는 회색 지구본 → "이게 우리 집 선풍기인지" 헷갈림

"옆집도 접속 가능한 거 아냐?"

· 기본 비번 2540이 너무 단순 → 보안 불안
· 나중에 설정에서 바꿀 수 있다는 걸 일주일 뒤에야 알았음

💡 개선 제안 (우선순위 上)

1. PWA 앱 설치 지원: iOS Safari "홈 화면에 추가" / Android Chrome "앱 설치" 배너 자동 안내 → 아이콘 + 앱처럼 실행
2. QR 코드 스티커: 제품 하단에 접속 QR 스티커 상시 부착
3. 초기 비번 랜덤화: SNW-XXXX 형식 (제품 시리얼 기반) → 옆집 무단 접속 차단
4. Android LTE 자동 전환 안내: 첫 접속 시 "모바일 데이터 끄고 접속하세요" 팝업

3️⃣ 첫 화면 — 대시보드

😕 불편했던 순간

"화면이 왜 이렇게 복잡해?"

· 첫 접속 3초 로딩 후 대시보드
· 상단: 상태 배지, 풍속, Phase, PWM, 스케줄, 프로필, AutoOff — 의미 모르는 용어 7개
· 하단: 슬라이더 3개 (강도, 변동성, 돌풍 빈도) — 이게 다 뭐지?

"프리셋 카드가 10개인데 뭘 골라야 하지?"

· 바다, 시골, 지중해, 산, 평원, 항구, 숲, 도시, 열대, 사막
· 이모지는 3개만 나오고 나머지는 똑같은 나뭇잎 🍃 → 구분 불가
· "바다 vs 항구 vs 지중해" 뭐가 다른지 모름

"강도/변동성/돌풍 슬라이더... 손대도 되는 건가?"

· 프리셋 클릭하면 슬라이더가 자동으로 바뀜 → "내가 조정한 게 사라졌네?"
· 슬라이더 재조작 → 다시 프리셋 클릭 → 또 리셋 → 혼란 무한루프

"PWM이 뭐예요?"

· 일반 사용자는 PWM, Phase, AutoOff, FSM 배지의 의미를 모름

💡 개선 제안 (우선순위 上)

1. 첫 방문 온보딩 3단계:
   · Step 1: "자연풍이란? → 실선풍기와 다릅니다"
   · Step 2: "프리셋 3개만 소개 (바다/숲/산)" + 체험 버튼
   · Step 3: "고급 조정은 나중에"
2. 프리셋 카드 이모지 완성: OCEAN 🌊 / MOUNTAIN 🏔 / FOREST 🌲 / HARBOR ⚓ / PLAINS 🌾 / DESERT 🌙 / URBAN 🌆 / TROPICAL 🌴 / MEDITERRANEAN 🏖 / COUNTRY 🏡
3. "고급 모드" 토글: 첫 방문 시 슬라이더 3개 숨김 → "고급 조정 표시" 버튼 클릭 시 노출
4. 용어 풀이 툴팁: PWM 옆에 (?) 아이콘 → "모터 출력 %"
5. 사용자 조정값 보호: 슬라이더 수동 조정 후 프리셋 재클릭 시 "기본값으로 초기화할까요?" 확인

4️⃣ 일상 사용 — 매일매일

😕 불편했던 순간

"프리셋을 바꿔도 바람이 안 세지는 느낌"

· 바다(강) → 산(더 강) 클릭했는데 체감이 거의 같음
· 실제로는 버그로 강도가 50%로 고정돼 있었음 (감사 U-001)
· 사용자는 "이 제품 원래 이런가?" 하고 넘어감 — 제품 결함을 사용자 탓으로 돌림

"지금 바람이 실제로 나오고 있는지 알기 어려움"

· 실시간 풍속 4.5 m/s 표시 → "그게 센 건가?" 감이 안 옴
· 선풍기 앞에 손을 대봐야 앎
· 미홈 앱은 "1단/2단/3단" 명확한데 여기는 %와 m/s 혼용

"정지 눌렀는데 진짜 멈췄나?"

· STOP → 슬라이더는 0이 되지만, PWM 게이지는 잔상이 남아 보임
· 팬 소리는 조용해져서 알 수 있는데, 무음 환경 아니면 확인 불가

"자꾸 화면이 초기 상태로 돌아가요"

· 다른 탭 갔다 오면 슬라이더가 기본값으로 리셋 (Store 미갱신 케이스)
· 실제로는 WS 재구독 중 일시적 현상이었지만 사용자는 버그로 인식

💡 개선 제안 (우선순위 上)

1. 직관적 강도 표시: 4.5 m/s → 4.5 m/s (보통 · 선풍기 2단 정도) 병기
2. STOP 후 명확한 피드백: "정지 완료" 토스트 + 팬 아이콘 회전 멈춤 애니메이션
3. "내 조정값 저장" 기능: 슬라이더 조정 후 "이 설정을 기본값으로" 버튼 (프리셋별 저장)
4. 실시간 소음/풍압 대안 표시: 소리 크기(dB 추정) 또는 "체감 시원함" 5단계 별점

5️⃣ 야간 수면 — 핵심 사용 목적

😕 불편했던 순간

"수면 모드가 어디 있지?"

· Forest 프리셋 + SLEEP 스타일 2개를 동시에 선택해야 "수면 모드"가 됨
· 이건 개발자만 이해하는 조합 — 매뉴얼 §5.2에 "Sleep(수면풍)"이라 쓰여 있지만 UI엔 따로 없음
· 결과: 3일 동안 일반 강도로 잤음 (너무 시원해서 감기 기운)

"새벽에 왜 팬이 꺼졌지?"

· Off-Temp 26℃ 기본 설정 → 새벽 4시 온도 떨어지면 자동 정지
· 하지만 "왜 꺼졌는지" 새벽엔 모름 → 아침에 배너 확인 (영문 AUTOOFF_TEMP)

"배너가 화면을 밝게 해요"

· 새벽에 AutoOff 배너 → 폰 화면 밝아짐 → 잠 깸
· 다크 모드는 있지만 야간 자동 밝기 조절 없음

"수면 타이머 120분 설정했는데 꺼지지 않았어요"

· 스케줄 3번(Night Sleep)은 22:00~07:00 자동
· 수동 타이머(120분)은 프로필 내부 AutoOff에서만 설정 가능 (숨겨져 있음)
· 대시보드에 "타이머" 버튼이 없어서 매번 스케줄 편집 화면 들어가야 함

💡 개선 제안 (우선순위 最上)

1. "수면 모드" 원클릭 버튼 대시보드 상단에 배치 — Forest+SLEEP+타이머+Off-Temp 자동 조합
2. 야간 자동 밝기 감소: 접속 시각 22:00~06:00엔 화면 밝기 30% 자동
3. AutoOff 배너에 한글 사유 + 조용한 모드: 야간엔 토스트 대신 LED만 조용히 표시
4. 대시보드에 "취침 타이머" 바로가기: N시간 후 자동 꺼짐 3버튼 (30/60/120분)

6️⃣ 스케줄/프로필 — 고급 기능

😕 불편했던 순간

"스케줄과 프로필의 차이를 모르겠어요"

· 매뉴얼: "스케줄은 요일별 자동, 프로필은 사용자 바람 시퀀스"
· 실사용: 둘 다 세그먼트로 구성되고, 둘 다 반복 가능 → 개념 중복
· "프로필"을 쓰려면 모드 스위치를 PROFILE로 전환해야 함 (발견까지 2주)

"세그먼트 편집이 너무 어려워요"

· "override", "windIntensity", "variability", "gustFrequency" — 영어 용어
· "Override 활성화하면 프리셋 무시" — 이게 뭔 소리?
· 세그먼트 1개 추가하는 데 5분 이상 소요

"저장이 자동인지 수동인지 모르겠어요"

· 슬라이더는 자동 저장, 스케줄 편집은 "저장" 버튼, 설정은 "저장 후 재적용"
· 어디는 저장, 어디는 자동 → 사용자 멘탈 모델 없음

"시간 설정이 어려워요"

· 세그먼트마다 onMinutes, offMinutes, autoOff.timer.minutes 등 3가지 시간
· "켜짐 시간" vs "타이머" vs "예약 종료 시각" — 뭐가 우선?

💡 개선 제안 (우선순위 中上)

1. 스케줄/프로필 통합 or 명확한 역할 분리:
   · 스케줄 = "달력 자동화"
   · 프로필 = "나만의 바람"
   · 대시보드에 두 개념을 다른 카드로 분리
2. 세그먼트 프리셋 템플릿: "아침 30분", "집중 60분", "취침 120분" 원클릭 추가
3. 모든 저장 자동 통일 + "적용하려면 여기" 배너: 저장/적용 이원화 제거
4. 시간 설정 통합: "몇 분 동안? / 몇 시까지?" 2가지만 (현재 3개는 과다)

7️⃣ 센서 — PIR, 온습도

😕 불편했던 순간

"인체 감지가 있는데 왜 자꾸 꺼져요?"

· 소파에 앉아 TV 보는데 15분 후 꺼짐 (holdSec 120초 기본)
· "움직여야 유지된다" 안내 없음 → "고장인가?" 의심
· 매뉴얼에 "움직임 감지"라 쓰여 있지만, 사용자는 "사람 있으면 유지"로 기대

"온도가 실제와 다르게 표시돼요"

· 실내 온도계 25.5℃인데 앱은 24.8℃ (DHT22 오차 ±0.5℃ → 오히려 정상)
· 2초 캐시 주기라 급격한 변화엔 반응 느림
· "온도가 맞는 건가?" 신뢰 문제

"PIR 강제 테스트가 개발자 도구 같아요"

· "PIR 강제 감지 테스트" 버튼 — 사용자는 언제 써야 할지 모름
· 실사용에선 "지금 내 움직임이 감지되고 있나?" 실시간 표시 필요

💡 개선 제안 (우선순위 中)

1. PIR 상태 실시간 표시 + 애니메이션: 감지 시 👤 아이콘 깜빡임 (현재는 값만)
2. holdSec 설정 슬라이더: 초 단위 숫자 입력 → 30/60/120/300 버튼 제공
3. 온도 신뢰도 표시: "DHT22 ±0.5℃" 병기
4. "PIR 강제 테스트"를 "지금 감지 확인"으로: 버튼 클릭 → 5초 카운트다운 → 감지 여부 표시

8️⃣ 문제 발생 시 — 트러블슈팅

😕 불편했던 순간

"팬이 안 돌아요" (가장 흔한 상황)

· 앱 화면: 팬 아이콘 ⏸ (노란색 배지), 상태: AUTOOFF_STOPPED
· 배너: 🛑 자동 꺼짐 · 사유: AUTOOFF_TIMER ← 영문 노출 (감사 U-012)
· 사용자: "AUTOOFF_TIMER가 뭐야?" → 매뉴얼 찾아야 이해

"Wi-Fi가 자꾸 끊겨요"

· 상태 점 🔴 → 🟡 (폴링 모드) → 재연결 시도
· "얼마나 기다려야 하지?" 표시 없음

3. 핵심 아키텍처 이슈 — "가상 체험"은 어디서 계산?

⚠️ Think Before Coding: 이 결정 없이는 설계 불가

"실선풍기 안 돌리고 그래프만 미리보기"가 가능하려면 물리엔진(S10)을 어디서 실행할지 결정해야 합니다.

3.1 선택지 4가지

옵션 물리엔진 실행 위치 백엔드 C++ 수정 프론트 JS 수정 정확도 즉시 반응
A. 오프라인 어댑터 재활용 998.offline_0202.js의 startSimulator() (이미 존재) ❌ 소 낮음 (간이) ✅
B. 백엔드 dry-run 모드 ESP32의 S10 실제 실행, PWM만 0 중 (S10 + W10) 소 100% ⚠️ (Wi-Fi 왕복)
C. 프론트 S10 미러 브라우저에 S10 로직 이식 ❌ 대 (유지보수 부담) 중 (드리프트 위험) ✅
D. 실선풍기 강제 가동 그냥 실제로 돌림 (PWM 실제) ❌ 없음 100% ✅ (소음 O)

3.2 각 옵션 실제 사용자 체험

A. 오프라인 어댑터 재활용

· 대시보드에서 "가상 미리보기" 클릭 → 브라우저 JS가 30초 파형 생성
· 장점: 백엔드 무수정, 즉시 반응, 실선풍기 무소음
· 단점: 프론트 간이 엔진 ≠ ESP32 S10 → 실측과 다를 수 있음
· 사용자: "미리보기랑 실제가 좀 다른데?" 신뢰 문제

B. 백엔드 dry-run 모드 (권장 후보)

· 프론트: POST /simulation { dryRun: true }
· 백엔드: S10 tick 실행, pwm.P10_setDutyPercent() 호출만 skip
· 결과 파형을 WS로 전송
· 장점: 실제 S10 로직 100% 일치, 프론트 계산 부담 0
· 단점: 백엔드 C++ 수정 필요 (원칙 1 예외 필요), WS 왕복 지연 (1.2초)
· 사용자: "실제랑 똑같은 파형이 미리 보인다"

C. 프론트 S10 미러

· 998.offline의 엔진을 확장 (Von Kármán 난류까지)
· 장점: 백엔드 무수정, 즉시 반응
· 단점: S10 코드 변경 시 프론트도 동기화 → 드리프트 위험, 유지보수 부담

· 장점: 100% 실제, 즉시

3.3 각 레이어 세부 설계

🅰️ Layer 1 — 상태 타임라인 (FSM 7-State 컬러 밴드)

7-State 색상 매핑 (000.const.js FSM_STATE_META와 정합):

State 색상 분류
IDLE 🩶 회색 비작동
OVERRIDE 🔵 파랑 작동 (수동)
PROFILE_RUN 🟢 초록 작동 (자동)
SCHEDULE_RUN 🟢 초록 작동 (자동)
MOTION_BLOCKED 🟡 노랑 일시정지
AUTOOFF_STOPPED 🟠 주황 정지 (래치)
TIME_INVALID 🔴 빨강 정지 (오류)

인터랙션:

· 밴드 hover → 툴팁: SCHEDULE_RUN (12:28:00 ~ 12:31:15, 3분 15초) · 이유: SCHEDULE_ACTIVE
· 밴드 클릭 → 확대 (해당 시간대만 표시)
· 회색/주황/빨강은 반투명 (비작동 강조)

🅱️ Layer 2 — 풍속/PWM 라인 (이중 축)

· 좌측 Y축: 풍속 (m/s)
· 우측 Y축: PWM (%)
· 두 선이 겹쳐서 "강도 조정 ↔ 풍속 변화" 관계 시각화
· 돌풍/열기포 발생 구간에 아이콘 마커 (🌀 = gust, 💨 = thermal)

🅲 Layer 3 — 중요 이벤트 로그 (스크롤 테이블)

이벤트 종류:

종류 조건 예시
State 전이 runCtx.state 변경 SCHEDULE_RUN → MOTION_BLOCKED
프리셋 변경 sim.presetCode 변경 OCEAN → MOUNTAIN
스타일 변경 sim.styleCode 변경 BALANCE → ACTIVE
강도 변경 sim.intensity ±5 이상 70 → 85
AutoOff 발동 stateCode==5 AUTOOFF_TIMER (480분)
세그먼트 전이 activeSegNo 변경 segNo 10 → 20
PIR 감지/부재 motionActive 토글 감지 → 부재 (120초 경과)

3.4 🔴 아키텍처 결정 필요 — 데이터 소스

⚠️ Think Before Coding: 이 결정 없이는 설계 불가

모니터링 그래프의 핵심은 "시간별 상태(state) + 이유(reason) 이력"입니다. 현재 백엔드는 이 이력을 저장하지 않음.

현재 백엔드의 이력 데이터

| 데이터 영역 | 이력 저장 여부 | 상세 저장 내용 |
|---|:---:|---|
| `S10::s_chartBuffer[120]` | ✅ | timestamp, wind, target, pwm, preset_index, gust_active, thermal_active |
| `runCtx.state/reason` | ❌ | 현재값만 유지 (과거 이력 없음) |
| `sim.intensity` 등 | ❌ | 현재값만 유지 |

문제: s_chartBuffer에 state_code와 reason_code가 없음 → 모니터링 그래프의 Layer 1, Layer 3 그릴 수 없음

선택지 3가지

옵션 데이터 소스 백엔드 C++ 정확도 세션 한계 즉시성
D-1 프론트 세션 버퍼 (WS /ws/state 800ms 샘플링) ❌ 없음 🟡 800ms 지연 페이지 열람 중만 ✅
D-2 백엔드 상태 이력 버퍼 (chart buffer에 state_code/reason_code 추가) ⚠️ ~30줄 🟢 100% 재부팅 시 초기화 ✅
D-3 하이브리드 (D-1 우선, D-2 옵션) ⚠️ 예외 시 🟢 - -

D-1 (프론트 세션) 상세

동작:

· WS /ws/state 구독 (이미 존재, 800ms 주기)
· 매 수신 시: _stateBuffer.push({t, stateCode, reasonCode, presetCode, intensity, pwm})
· 120개 순환 (≈96초)
· #/monitor 페이지 mount 시 수집 시작, unmount 시 중단

장점: 백엔드 무수정 (원칙 1 완벽 준수)
단점: 페이지 진입 전 이력 없음 (새벽 3시 이슈 → 아침에 못 봄)

D-2 (백엔드 버퍼) 상세

C++ 수정 (30줄):

```cpp
// S10_Simul_0202.h: ST_ChartEntry에 2필드 추가
struct ST_ChartEntry {
    ...
    uint8_t state_code;    // 신규
    uint8_t reason_code;   // 신규
};

// S10::tick()에서 chart entry 생성 시:
v_e.state_code  = CT10_currentStateCode();   // CT10 접근자 신규 필요
v_e.reason_code = CT10_currentReasonCode();
```

문제: S10 → CT10 의존성 추가 (모듈 경계 침범)

대안: CT10::exportChartJson에서 s_chartBuffer 순회 시 runCtx의 현재 상태를 덧씌움... 하지만 과거 시점 상태는 알 수 없음

더 나은 대안: CT10::tickLoop에서 별도 s_stateHistory[120] 버퍼 관리 (S10과 독립)

```cpp
// CT10_Ctl_0202.h
struct ST_CT10_StateHistoryEntry {
    uint32_t t;           // epoch ms
    uint8_t  stateCode;
    uint8_t  reasonCode;
    uint8_t  activeSchId;
    uint8_t  activeSegNo;
    float    intensity;   // sim.userIntensity 스냅샷
};

// CT10::tickLoop()에서 1Hz 스냅샷
```

→ 백엔드 30~50줄 + W10 라우트 1개 추가

장점: 새벽 이슈를 아침에 확인 가능 (재부팅 전까지)
단점: 백엔드 C++ 수정 → 원칙 1 예외 승인 필요

struct ST_MON_Wind5Min_t {

// Wind 30분 뷰: 5초 평균
for (int i = 0; i < 360; i++) {
    int start = i * 5;  // 초
    int end   = (i + 1) * 5;
    float sum = 0, minV = 999, maxV = -999;
    int cnt = 0;
    for (int j = start; j < end; j++) {

        minV = min(minV, buffer[j].wind);
        maxV = max(maxV, buffer[j].wind);

}

7. 🔴 Flash 마모 분석 (배치 쓰기 주기 결정)

7.1 문제: LittleFS에 얼마나 자주 쓸 것인가?

쓰기 주기 하루 쓰기 횟수 예상 수명 (100K cycles)
5분마다 288회 347일 (1년) ❌
30분마다 48회 2,083일 (5.7년) ⚠️
1시간마다 24회 4,166일 (11.4년) ✅

결론: 1시간 배치 쓰기 권장

7.2 배치 쓰기 동작

```
[Hour H:00~H:59 동안]
RAM Hot buffer에 5분 평균 12개 누적
    ↓
[H+1:00:00]
LittleFS에 12개 엔트리 일괄 append (한 번의 write)
    ↓
Flash 마모 최소화 (하루 24회 쓰기)
```

trade-off: 최근 1시간 데이터는 PSRAM에 있으므로 조회엔 영향 없음. 재부팅 시 최대 1시간 손실 가능 (다음 flush 전 재부팅 시).

⚠️ 재부팅 손실 완화:

· 재부팅 감지 시 (setup()에서 first_epoch과 last_epoch 비교)
· 이전 세션 마지막 flush 이후 손실이 있으면 로그로 WARN
· 심각한 경우 System 이벤트에 UNEXPECTED_REBOOT 기록

4. LittleFS 파일 구조 및 용량 (확정)

4.1 파일 목록

```
/lfs/monitor/
├── wind_history.bin      (32.3KB, 2016 엔트리 × 16B)
├── state_history.bin     (33.6KB, ~1680 엔트리 × 20B)
├── config_history.bin    ( 7.2KB, ~600 엔트리 × 12B)
├── sensor_history.bin    (32.3KB, 2016 엔트리 × 16B)
└── system_history.bin    ( 1.8KB, ~150 엔트리 × 12B)
                        ─────────
                        107.2KB
```

4.2 공통 헤더 (64B)

```cpp
struct ST_MON_FileHeader_t {
    uint32_t magic;                 // "MNW1"
    uint16_t version;               // 1
    uint16_t entry_size;            // 16/20/12/16/12
    uint32_t capacity;              // 최대 엔트리 수
    uint32_t head;                  // 최신 위치 (ring buffer)
    uint32_t count;                 // 실제 엔트리 수
    uint32_t first_epoch;
    uint32_t last_epoch;
    uint8_t  _pad[38];
};
```

4.3 Ring Buffer 동작

```
[append] head=(head+1)%capacity
         if count<capacity: count++
         else: 첫 엔트리 덮어쓰기 (가장 오래된 것 소실)
[read]   순서대로 oldest → newest
```

5. Flush 정책 (Q-I-1 확정)

5.1 1시간 배치 동작

```
[Hour H:00 ~ H:59]
  RAM Hot → PSRAM Warm 이동 (1초마다)
  RAM Hot 5분 평균 누적 (12개/시간)
       ↓
[Hour H+1:00:00]
  LittleFS에 12개 일괄 append (한 번의 파일 write)
       ↓
  최대 1시간치 손실 가능 (재부팅 시)
```

5.2 재부팅 손실 완화

· setup()에서 Cold 파일 last_epoch 확인
· 현재 시각 - last_epoch > 1시간이면 WARN 로그
· System 이벤트에 UNEXPECTED_REBOOT 기록

5.3 Flash 마모 재확인

| 점검 항목 | 산출값 / 계산 근거 |
|---|---|
| 하루 flush 횟수 | 24회 |
| 1회 flush 크기 | 5개 파일 × 12 엔트리 = ~1KB |
| 예상 Flash 수명 | 100,000 cycles ÷ 24/일 = 4,166일 (11.4년) ✅ |
